# 旅行助手业务功能技术实现方案

> 2026-11-04 状态：除 V3 与票务交易外，本文描述的 V1、V2 功能均已实现，实现口径以代码与
> [接口文档](服务端REST接口文档.md) 为准。以下保留决策时的原始表述，便于回溯取舍过程；
> 与实现有出入的地方已在各节末尾用「实现口径」标注。

## 1. 账号与身份

服务端提供注册、登录接口，用户名唯一；密码使用 BCrypt 哈希。登录后签发随机会话令牌，客户端在请求中携带；令牌过期需重新登录。服务端将用户身份与方案成员关系作为授权依据。令牌和密码不写入日志。

## 2. Agent 生成行程

2026-11-02 决策：Spring AI 加 Java 显式流程编排需求理解、景点推荐、行程规划三个角色，V2 增加票务 Agent 购票辅助。Python 离线构建，Java 通过 AttractionRepository 加载快照并限制检索结果数量；PlanningState 保存结构化需求、候选 ID、证据和校验结果。先完成单 Agent 基线，再比较拆分效果，不引入额外编排框架。具体角色及数据治理见[专项方案](多Agent与票务能力方案.md)。

客户端发送自然语言需求；服务端调用 DeepSeek，将目的地、时间、类型、预算及安排解析为草案。缺少必要字段时返回补充问题。模型输出须经过结构和字段校验，无法解析时提示重试，不保存不完整结果。用户编辑并确认后调用保存接口。模型调用设置超时、有限重试和调用次数上限；密钥使用环境变量。

V2 将高德地点、天气、路线查询封装为工具，模型根据需要请求工具，服务端校验工具参数并执行，再将结果返回模型生成建议。显示来源和查询时间；失败时如实提示。V3 在提示词中提供经授权读取的预算和投票数据，建议仍需用户确认。

> **实现口径**：工具选择由 Java 显式编排（景点 → 天气 → 票务），**不交给模型**。
> 模型只拿到已经查到的数据并负责组织语言，这样每条建议都能追溯到来源。
> 代价是灵活度低一些：当前不支持「模型临时决定再查一次路线」这种动态链路，属 V2 剩余部分。
> 模型调用走 OpenAI 兼容 HTTP 接口而非 Spring AI `ChatClient`，原因是后者缺密钥时会导致上下文启动失败。

## 3. 行程、费用与时间

建立旅行方案基础类及短途周末游、长途跨省游子类；交通、住宿、景点为安排对象。以 decimal 金额保存费用，使用统一时区和明确日期时间。总预算为已填写预计费用之和，缺失项单独提示；V3 分别统计实际费用和按当前成员人数计算人均费用。

V1 校验方案起止时间、类型、必填字段及非负金额。V2 对安排校验起止时间和所属方案时间范围，检测时间区间重叠并提示确认。实际交通衔接是否可行需结合路线及用户判断。

> **实现口径**：只有「结束早于开始」在写入时返回 400。「重叠」和「越界」只进体检提示，
> 不拦写入——服务端直接拒绝会挡掉正在编辑的中间状态（例如正在调换上下午顺序）。
> 重叠用扫描线找「与当前最晚结束项相交」的对，不会把互相重叠的 n 项展开成 n² 条提示。

## 4. 邀请与并发

创建者按用户名邀请；服务端验证目标账号及权限，创建待处理邀请。受邀者接受后加入成员集合，拒绝后保留处理结果。方案版本从创建时开始递增；更新请求必须提交读取时版本，服务端在同一写入锁内比较、保存并递增；不一致返回冲突，客户端重新读取后由用户决定如何合并。

## 5. 本地文件与恢复

服务端使用 UTF-8 JSON 文本文件保存用户、邀请和方案；启动时读取并校验结构。服务端串行化写入：写临时文件、刷新后替换正式文件；失败保留原文件并报告错误。损坏文件不自动覆盖，提示从备份恢复。敏感凭据通过环境变量提供；人工定期备份数据目录。

## 6. 后续功能

V2 保存留言及含操作者、时间、变更摘要的操作记录。V3 保存候选项和成员投票，提供预算统计、文本导出与归档；投票不自动改变方案。导出由客户端选择本地路径，服务端生成授权范围内的摘要。

> **实现口径**：留言与操作记录各自落盘（`comments.json` / `changelog.json`），**都不进行程聚合**，
> 因此都不推进 `version`。操作记录由服务端在写操作成功后产生，`actor` 取会话身份，客户端无法提交。

## 7. 验证

使用 JUnit 验证预算、时间、权限、邀请及版本冲突；使用临时目录测试保存、重启读取与损坏文件处理；模拟模型和高德超时、错误与非法结果。另在配置真实凭据后验证外部接口和两台电脑联调。

## 8. 购票辅助与后续交易

V2 票务 Agent 提供经核验的官方入口及已查询规则，用户跳转购买；未知库存明确标记，无可靠入口时不猜测链接。此阶段不创建订单或处理支付。

V3 之后在获得正式接口与授权后，另行实现 TicketingGateway、订单服务和持久化：复核产品、场次、价格和库存，展示订单预览，取得用户确认后下单并跳转支付，核验出票后更新行程与预算。下单幂等、超时查单、回调验签与去重、状态恢复和退款核验由 Java 服务执行。身份证等资料通过受控表单收集，不进入模型上下文或普通日志。完整交易前评估数据库和事务，不能直接沿用聊天记忆或假定当前 JSON 文件已满足要求。
