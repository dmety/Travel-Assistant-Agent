## 一、今日工作

基线：`wei` 分支，起点提交 `7824315`（docs: 统一术语与版本口径）。此前仓库里只有景点 JSON 与 Python 检索脚本，
Java 侧没有任何加载与查询能力（`README` 与《知识库使用文档》均标注"Java 在线检索尚未实现"）。本轮把这半条链路补齐。

### 1. Python 侧：新增离线精简构建

新增 `tools/build_attraction_index.py`，只读 `data/china_attractions.json`，输出 `data/attractions_index.json`。
分工保持"Python 离线构建、Java 在线检索"不变，没有把查询逻辑搬到 Python。

构建做了四件事：

| 处理 | 规则 | 命中量（本次实测） |
|---|---|---|
| 占位值规范化 | `暂无 / 未知 / 无 / - / -- / null / N/A` 等统一转 `null` | 字段占位命中 14437 次 |
| 等级伪值清理 | `level = "其他"/"其它"` 不构成真实等级，置 `null` | 10606 条 |
| 伪地址清理 | 地址等于城市/省份或其拼接（如「北京市北京」）时置 `null` | 3831 条 |
| 冗余字段裁剪 | 去掉每条重复的 `city_intro`、`photos`、`tags`、`same_name_group` 等 | 13MB → 5.7MB |

关键约束：**不覆盖原库**。脚本对输入只读；输出路径与输入相同时直接拒绝并返回退出码 4；
写入走临时文件 + `os.replace` 原子替换，只动输出文件。输入缺失返回 2、损坏返回 3。

### 2. Java 侧：启动加载 + 三索引

新增 `infrastructure/persistence/AttractionStore`，`@PostConstruct` 加载精简库，在内存建三套索引：

- `idIndex`：`id → Attraction`；
- `cityIndex`：城市/省份（**含别名**）→ 列表；
- `nameIndex`：小写名称 → 列表（精确命中用），全量列表兜底前缀/包含匹配。

**降级策略（需求明确要求）**：缺库、解析失败、缺 `attractions` 数组、全部记录不可用时，
Store 只把状态置为不可用并记录原因，**不创建、不重写、不"修复"任何文件**。查询接口此时返回 503 并带 `reason`，
而不是返回空列表——否则调用方会把"库没加载"误判成"库里没有这个景点"。

### 3. 查询接口与条数限制

新增 `interfaces/rest/AttractionController`（`/api/attractions`）：

| 接口 | 说明 |
|---|---|
| `GET /api/attractions?city=杭州&limit=20` | 按城市/省份查询，`city` 与 `name` 都给时 `city` 优先 |
| `GET /api/attractions?name=西湖&limit=20` | 按名称查询 |
| `GET /api/attractions/{id}` | 按 ID 查详情，不存在 404 |
| `GET /api/attractions/status` | 加载状态、条数、不可用原因 |

条数限制收敛在 `AttractionService`：默认 20，上限 50，非正数回落默认；`matched` 保留截断前总数，
`returned` 是实际返回数，两者分开，避免调用方误以为"就这么多"。

`AttractionView` 同时给出原始值（`ticket`/`openTime`，可能为 `null`）与展示值（`ticketText`/`openTimeText`，缺失即"未知"），
让任何消费方都不会把 `null` 读成"免费"或"全天开放"。

# 同日第二轮（19:40 起）：V1 第 5 节「预算与时间检查」

- 阶段目标：补齐 V1 验收里还缺的两项——**出发/返回时间字段**与**预算自动汇总**，并给出可解释的行程体检
- 基线：`wei` 分支 `9482763`（第一轮景点查询链路已推送）
- 起点判断：`README` 的未实现清单明确列着「预算自动汇总」「出发/返回时间字段」，`domain/budget` 只有一个空 `package-info`（"具体代码后面再写"），没有任何计算逻辑

## 一、本轮工作

### 1. 领域模型：方案补起止日期

`Plan` 由 3 字段扩到 5 字段（`departDate` / `returnDate`，`LocalDate`）。兼容处理做了两件事：

- 保留三参数构造，旧调用（`Itinerary.create` 的兜底、老测试）不用改；
- 两个字段允许为空：**历史行程的 JSON 里没有这两个键，反序列化为 `null` 而不是读取失败**，缺失交给体检接口提示「未填写」。

### 2. 预算汇总：多币种不合并

新增 `domain/budget/BudgetCalculator`（纯计算，不依赖 Spring 与文件系统），汇总时按「币种 + 类别」双维度分组。

| 规则 | 决定 | 理由 |
|---|---|---|
| 跨币种相加 | **不做**，分币种成行 + `notes` 说明 | 100 元 + 100 美元 = 200 是错的；汇率换算要外部汇率源和时间点，属 V2 之后 |
| 同类不同币种 | 拆成两行（`交通/CNY`、`交通/USD`） | 同上，按类别合并会把不同币种加在一起 |
| `amount` 为 `null` | 进 `pending`，**不计入合计** | V1 要求"未填写费用标记为待填写"，不能当成 0 混进总额 |
| `amount` 为负 | 照实计入合计，并写入 `notes` | 写入已被 D-4 拦截，能出现的只可能是历史数据；静默丢弃比报错更危险 |
| `category` 为空 | 归入「未分类」 | 避免出现无标题的分类行 |
| `primaryCurrency` | 条目最多的币种，平票 `CNY` 优先，再按字典序 | 保证同一份数据每次结果一致，测试可断言 |

金额统一 `setScale(2, HALF_UP)`，接口输出 `1400.00` 而不是 `1400.0`。

### 3. 写入校验：返回早于出发直接 400

`ItineraryService.validatePlanPeriod` 在 **create 与 updatePlan 两处**生效：两者都填且返回早于出发时抛
`InvalidItineraryException` → **400**，**版本号不变**（校验失败不落库）。

选择写入时拦截、而不只是查询时提示：错误数据一旦落盘，之后每次汇总都要重新解释它。

### 4. 行程体检

`ItineraryChecks` 给出 `ok` 与 `warnings[]`，每条带**稳定 code**（文案可改、代码不变）：

`DEPART_DATE_MISSING`、`RETURN_DATE_MISSING`、`RETURN_BEFORE_DEPART`、`EXPENSE_AMOUNT_MISSING`、
`EXPENSE_NEGATIVE`、`NO_EXPENSE`、`MIXED_CURRENCY`、`DAILY_OUT_OF_RANGE`、`TRANSPORT_OUT_OF_RANGE`、
`LODGING_OUT_OF_RANGE`、`LODGING_PERIOD_INVALID`。

一个刻意的取舍：**日期区间倒置时只报 `RETURN_BEFORE_DEPART`，不再逐条报越界**。否则每条安排都会再报一次，
噪声会盖住真正的问题。

### 5. 接口与界面

| 层 | 内容 |
|---|---|
| 应用层 | `application/budget/BudgetService`：先经 `ItineraryService.get` 取聚合根，**复用行程查看权**，越权即 403 |
| 接口层 | `GET /api/itineraries/{id}/budget`（响应头 `X-Version`）、`GET /api/itineraries/{id}/checks`（体内 `version`） |
| 测试台 | `app.html` 新增「预算检查」页签：按币种/分类列合计 + 口径说明 + 体检提示；方案页签补字段说明 |
| 控制台 | 登录成功后自动取「我的行程」第一份，打印预算汇总与体检结果 |

两个接口都是**只读**的，不递增版本号（有专门用例守着）。

# 同日第三轮（20:00 起）：V1 第 4 节「邀请与多人协作」

- 阶段目标：补齐 V1 最后一块——**创建者按账号邀请 → 受邀者接受或拒绝 → 成员可主动退出**，并把邀请落盘
- 基线：`wei` 分支 `92745f4`（第二轮预算与时间检查已推送）
- 起点判断：需求 §4 原文三条——「创建者按账号邀请其他用户；受邀者登录后接受或拒绝」「创建者可移除成员；成员可主动退出」「服务端将账号、**邀请**和方案等数据保存为本地文本文件」。此前 `addMember` 是 owner 直接拉人，没有受邀者确认环节，也没有 `invitations.json`

## 一、本轮工作

### 1. 领域模型：邀请是独立聚合

新增 `domain/invitation`：`Invitation`（record）+ `InvitationStatus`（`PENDING`/`ACCEPTED`/`REJECTED`/`CANCELLED`）。

状态机只有一条正向路径，没有回退：

```
PENDING ──accept──▶ ACCEPTED
        ──reject──▶ REJECTED
        ──cancel──▶ CANCELLED（创建者撤回 / 行程被删）
```

**为什么不把「待接受」直接写成 `Member`**：成员意味着已获得权限，待处理邀请只是一项请求。混在一起会让「谁真正能编辑」无法从数据里判断，也记录不下拒绝结果。

### 2. 邀请独立落盘，不进行程聚合

新增 `infrastructure/persistence/InvitationStore` → `data/invitations.json`，与账号/行程同样的「内存副本 + 临时文件 + `ATOMIC_MOVE`」写入。

这样做换来一条重要性质：**发出或撤回邀请不改变行程 `version`**。若邀请塞进行程，创建者每发一次邀请都会推进版本号，正在编辑的人下一次保存就会撞 409 —— 一次社交动作变成一次并发冲突，不合理。

### 3. 接受邀请不要求版本号

`ItineraryService.joinAsMember` 在**行程写锁内**以「当前版本 + 1」写入，不接受 `version` 参数：

- 若要求版本号，受邀者得先从「我的邀请」拿到行程版本，而创建者随时可能改动，一步能成的事会变成反复冲突；
- 版本号仍严格递增，乐观锁语义没有被破坏（并发编辑板块仍必须带 `version`）。

### 4. 接口

| 接口 | 方法 | 鉴权 |
|---|---|---|
| `/api/itineraries/{id}/invitations` | POST | 仅创建者（201 首次 / 200 复用待处理） |
| `/api/itineraries/{id}/invitations` | GET | 仅创建者 |
| `/api/invitations` | GET | 需登录（我收到的待处理） |
| `/api/invitations/{invId}/accept` | POST | 仅受邀者 |
| `/api/invitations/{invId}/reject` | POST | 仅受邀者 |
| `/api/invitations/{invId}` | DELETE | 仅创建者（撤回） |
| `/api/itineraries/{id}/leave` | POST | 仅成员（204） |

新增异常 `InvitationNotFoundException`(404)、`InvitationConflictException`(409)，接入统一异常处理。

### 5. 成员退出

`POST /api/itineraries/{id}/leave` 让成员主动退出（需求 §4 明确要求）。**创建者不能退出**（400）：行程必须始终有归属人，否则会变成无人可管理、也无人可删除的孤儿数据；要终止应当删除行程。

### 6. 删除行程时级联取消邀请

`ItineraryController#delete` 在删除成功后调用 `InvitationService#cancelPendingOf`。否则受邀者的「我的邀请」里会留下一条永远接受不了的邀请。

### 7. 界面与控制台

- `app.html` 新增「邀请」页签：发起邀请（带板块勾选）、本行程邀请记录（待处理的可撤回）、我收到的邀请（接受/拒绝）；成员页签加「退出该行程」按钮。
- 控制台新增：`invitations <账号> <密码>` 列出待处理、`... accept|reject <邀请ID>`、`invite <创建者> <密码> <行程ID> <受邀账号> [板块...]`。

## 四、本轮问题与处理

| 编号 | 严重度 | 问题 | 处理 |
|---|---|---|---|
| I-1 | P1 | 把「待接受」直接写成 `Member`，会让「谁真正能编辑」无法判断，拒绝结果也留不下 | 邀请独立聚合，只有 `accept` 才写 `members` |
| I-2 | P1 | 邀请若存进行程，发/撤邀请会推进 `version`，让正在编辑的人无故撞 409 | 邀请独立落盘，不进行程聚合 |
| I-3 | P1 | 接受若要求 `version`，受邀者会与创建者的编辑反复冲突 | 接受不带版本号，在写锁内以当前版本 +1 写入 |
| I-4 | P2 | 重复点「邀请」会堆出多条待处理邀请 | 命中同一待处理邀请时复用记录（200），只更新授权板块 |
| I-5 | P2 | 行程删除后邀请悬空，受邀者看到一条永远接受不了的邀请 | 删除时级联置为 `CANCELLED` |
| I-6 | P2 | 创建者退出会让行程变成无人可管理的孤儿数据 | 400 拦截，提示改为删除行程 |
| I-7 | P3 | `InvitationView` 若把行程标题存快照，行程改名后会展示过期标题 | 查询时从行程仓库实时取；行程已删则为 `null` |

## 五、后续安排

1. **直接授权与邀请并存的口径**：`POST /{id}/members` 保留为创建者直加（管理场景 + 既有客户端），主流程走邀请。若后续要求「一切加入都必须经对方同意」，只需下线该端点并同步 `ApiTestBase#addMember` 与 7 处调用。
2. **邀请有效期**：当前邀请不会过期，长期堆积会在「我的邀请」里留历史邀请。V2 可加 `expiresAt` 与到期自动 `CANCELLED`。
3. **通知**：受邀者需主动刷新才能看到邀请，没有站内消息或邮件推送。
4. **V1 剩余**：V1 五节功能至此全部落地，接下来按版本规划进入 V2（Agent 编排、高德接入、候选与投票）。

# 第四轮：V2 信息查询与行程完善

- 时间：2026-11-04 晚
- 基线：`wei` 分支，起点提交 `f8159c9`（feat(invitation): 实现 V1 §4 邀请与多人协作）
- 范围：V2 五节 —— 高德信息查询、Agent 工具调用、详细时间检查、协作记录与留言、票务购票辅助

## 一、本轮工作

V1 五节在上一轮全部落地后，按版本规划进入 V2。V2 有一个绕不开的现实问题：**高德和 DeepSeek 都需要密钥，
而本机没有**。如果按「先接密钥再写功能」的顺序，这一轮只能停在设计文档上。

所以先把「没有密钥时怎么办」当成一等需求来设计，再写有密钥时的路径。最终形态是：

| 依赖 | 缺失时的行为 |
|---|---|
| `AMAP_KEY` | `/api/location/**` 返回 503 + 原因，说明哪些功能停用、哪些不受影响 |
| `DEEPSEEK_API_KEY` | `/api/agent/plan` 仍返回带 ID 与来源的候选，`advice` 为 `null`，原因写进 `notices` |
| 购票入口配置 | 所有景点都提示「无经核验入口，请自行前往官方渠道」 |

这三条保证了「本机不配任何密钥也能完整跑起来」，也让测试可以强制断网运行。

### 1. 详细时间检查（V2 §3）

`DailyActivity` 新增 `startTime`/`endTime`（`LocalTime`，可空）。原有的自由文本 `time`（「上午」「9 点前」）
保留不动——有些安排本来就定不下具体时刻，强行要求填时间只会让人乱填。

三个判断，处理方式刻意不同：

| 情况 | 处理 | 理由 |
|---|---|---|
| 结束早于开始 | **写入即 400** | 纯笔误，没有合理解释 |
| 同一天内时间重叠 | 只做体检提示 | 需要用户自己判断是否要调换顺序 |
| 安排日期超出旅行范围 | 只做体检提示 | 可能是有意的跨天交通安排 |

重叠检测没有用「两两比较」（n 项互相重叠会炸出 n² 条提示），而是排序后做扫描线：
维护「当前已覆盖的最晚结束时间」及其来源项，遇到 `start < maxEnd` 就报一对。
这样 A(9-18)、B(10-11)、C(12-13) 会报出 A-B 与 A-C，但不会报 B-C（它们不重叠）。

首尾相接不算重叠：前一项 12:00 结束、后一项 12:00 开始是正常的。
整天只有自由文本时间时**不判**缺失——那是有意的模糊安排，不是漏填。

### 2. 协作记录与留言（V2 §4）

留言（`Comment`）与修改记录（`ChangeEntry`）各自落盘到 `comments.json` / `changelog.json`。

**关键决策：两者都不进行程聚合，都不推进 `version`。**
如果评论让版本号 +1，一个人在群里说句话，另一个人正在编辑就会撞 409——讨论和编辑是两件事，
不该互相干扰。同理，改动也不会因为有人留言而被迫重新读一遍。

修改记录由服务端在写操作成功后自动产生，`actor` 一律取会话身份。**客户端提交不了、也伪造不了**——
让被审计的人自己写审计日志，就失去了记录的意义。`ItineraryService` 通过一个 `ChangeLogRecorder` 端口
接入记录能力，避免它直接依赖查询侧服务形成循环依赖。

记录写入失败只记 WARN，不回滚：记录是旁路信息，为了一条日志让人丢掉一次已经落盘的编辑，不划算。

### 3. 票务购票辅助（V2 票务 Agent）

这一节的核心不是「能不能查到」，而是**「查不到时怎么说」**。

- 入口来自 `ticket_channels.json`，**仓库不内置任何链接**，默认文件不存在
- 文件不存在 / 解析失败 / 地址不是 http(s) 绝对地址 → 都视为「没有」，绝不生成猜测链接
- `stockVerified` 恒为 `false`：没接库存接口，「余票未核验」就是事实，不是暂时缺失
- 票价未知保持 `null`，**不补成 0**——0 元会让预算把「不知道」算成「免费」

有人会问：这样功能是不是等于空的？不是。它做的是把「系统知道什么、不知道什么」说清楚。
一个猜出来的购票链接比不给更糟——用户点进去可能买到加价票或者钓鱼页面。

### 4. 高德信息查询（V2 §1）

`AmapClient` 三条链路：地点检索、天气预报、路线规划，另加地理编码用于把城市名解析成 adcode
（天气接口只认 adcode，传「杭州」会返回空数组）。

- 未配置密钥：`ensureConfigured()` 直接抛，映射成 503。**不能返回 200 + 空结果**——
  那会被理解成「当地没有这个地方」
- 错误码翻译：高德的 `infocode` 抛给用户没有意义，但开发排查需要它，所以翻成人话的同时保留原始值
- 坐标：结果标注 `GCJ-02`，不能与 WGS-84 直接混用
- 公交必须给 `city`；坐标格式非法直接拒绝，不把错误坐标发给高德
- 密钥只出现在请求参数里，不写日志、不进异常消息

### 5. Agent 工具调用（V2 §2）

**工具选择由 Java 决定，模型只负责组织语言。** 顺序固定：景点检索 → 天气 → 票务 → 需求缺口提示 → 模型建议。

为什么不把「调哪个工具」交给模型：本项目要求每条建议可追溯。模型自由选工具就容易出现「没查就答」；
由 Java 固定链路，每一环的输入输出都经过校验，模型拿到的全是已经查到的数据，
自然说不出一个库里没有的景点 ID。

候选排序也补了一刀。原来按库里顺序取前 10 条，北京拿到的是「世界公园、世界花卉大观园、中央电视塔」——
知识库按名称排列，直接截断等于按拼音选景点。改成「等级（5A > 4A > 3A）→ 评分 → 名称」后，
前 10 条是「天坛、故宫、颐和园、圆明园、奥林匹克森林公园、恭王府、慕田峪长城……」。

模型调用没有用 Spring AI 的 `ChatClient`，而是直接走 OpenAI 兼容的 HTTP 接口。
原因是 `spring-ai-deepseek` 的自动配置在缺少密钥时会导致上下文启动失败，而本项目要求
「不配密钥也能启动」。依赖仍然保留，以后要换回 `ChatClient` 只需替换 `DeepSeekClient` 一个类。

### 6. 前端与控制台

`app.html` 新增三个页签：协作（留言 + 修改记录）、购票（入口查询）、周边查询（地点/天气/能力状态）。
打开行程时自动加载协作信息。

### 1. 领域模型：候选与票是独立聚合

V3 §1 最容易做错的地方是把候选塞进 `Itinerary`。那样一投票就推动 `version`，
两个人在群里讨论一下午就能让对方编辑器里的版本号失效。所以候选与票建在
独立包 `domain/decision`，与 `CommentsStore`、`ChangelogStore` 同一原则：**旁路数据不进行程聚合**。

| 类型 | 职责 |
|---|---|
| `CandidateKind` | `ATTRACTION("景点")` / `LODGING("住宿")` / `OTHER("其它")` |
| `Candidate` | record：id、itineraryId、kind、name、city、attractionId（可空）、note、proposedBy、createdAt |
| `VoteChoice` | `SUPPORT("支持")` / `OPPOSE("反对")` / `ABSTAIN("弃权")` |
| `Vote` | record：voter + candidateId + choice + votedAt + updatedAt；`withChoice()` 保留首次 `votedAt` |
| `VoteTally` | 纯计算：把票聚成每个候选的 `CandidateTally` |
| `CandidateBoard` | 给前端/客户端的完整视图：参与者数、已投票人数、候选数、总票数、排序结果、`leaderId`、`tie`、提示 |

两处刻意设计：

**其一，不做 1~5 星打分。** 星级的平均值在小样本上毫无意义（3 个人打 4 分和 1 个人打 4 分是同一个 4.0），
而且会诱导成员以为分数有裁决力。三选一（支持/反对/弃权）能说清「谁明确反对」，这才是讨论需要的信号。
排序用**净支持（支持 − 反对）**，因为「3 支持 2 反对」和「4 支持 4 反对」不是一回事。

**其二，平票不给赢家。** 一旦 `leaderId` 为 `null` 且 `tie=true`，接口就明确说「没有唯一领先项」，
而不是用「谁先提的」「谁票多就谁」替一群人做决定。系统可以排序给人看，但没有资格宣布结论。

### 2. 预算分析：上限、预计、实际、人均

`Expense` 加了一个 `actual` 布尔标记，`Plan` 加了 `budgetLimit` / `budgetCurrency`，
`BudgetCalculator` 新增 `analyze(Itinerary, Integer travelersOverride)`，产出 `BudgetAnalysis`：
预计总额、实际总额、与上限的差额、人均（预计/实际）、超支提示、口径说明。

四个不糊弄的点：

1. **「实际支出」靠显式标记，不靠日期猜。** 「日期早于今天就算已花」会把补录的旧票据和
   提前写下的预算算成一样的结果——它们的日期看起来可能完全相同。
2. **上限为空就是「未设定」，不拿 0 冒充。** 0 的语义是「一分不花」，和「还没填」差得远。
3. **多币种不硬减。** 上限币种与费用主币种不一致时 `comparable=false`、`remaining=null`，
   并给出原因，而不是拿汇率脑补一个数。
4. **人均人数默认 `members.size() + 1`。** 成员表里不含创建者自己；不带这个 +1，人均会凭空贵一截。
   接口允许 `?travelers=` 覆盖，用于「还有两个人待定」这类情况。

警告码：`BUDGET_LIMIT_MISSING`、`BUDGET_CURRENCY_MISMATCH`、`BUDGET_OVER_LIMIT`、
`BUDGET_ACTUAL_OVER_LIMIT`、`BUDGET_ACTUAL_OVER_PLAN`。`check()` 末尾补了 `TRIP_ENDED`
提示（返回日期已过且未归档），把「该归档了」这件事说出来。

### 3. 综合决策建议：规则算结论，模型只写措辞

`DecisionService.review()` 把四类事实汇到一处：投票榜、预算分析、行程体检、天气（可选）。
风险条目由 **Java 规则**产出，每条带 `severity`、`basis`（依据哪类数据）、`suggestion`：

| 风险码 | 级别 | 触发条件 |
|---|---|---|
| `TRANSPORT_ARRIVAL_CONFLICT` | HIGH | 交通到达时刻晚于当天已有安排 |
| `NO_LODGING` | MEDIUM | 多晚行程没有任何住宿条目 |
| `WEATHER_BAD` | MEDIUM | 旅行日期内有雨雪 |
| `VOTE_TIE` | MEDIUM | 候选并列，无法判断倾向 |
| `BUDGET_*` | HIGH/MEDIUM | 复用预算分析的警告码 |
| `NO_CANDIDATE` / `NO_TRANSPORT` / `ITINERARY_ARCHIVED` | INFO | 缺数据或已归档的说明 |

模型（DeepSeek）只负责把这些事实组织成可读文字。**未配置密钥时 `advice=null`，但风险与建议照常完整**，
`notices` 里说明「模型未配置，以下结论由规则生成」。这样「建议功能」不会因为一个外部服务没配就整体失效。
上限设了 `MAX_RISKS=30`、`MAX_SUGGESTIONS=8`，避免一份行程几十条重叠提示把人淹没。

### 4. 归档：全站只读，409 而非 403

`Itinerary` 加 `archived` / `archivedAt`，`withArchived()` 推进版本号。
归档后**所有**写入口一律拦下：五大板块、成员增删改、候选与投票，统一走 `requireNotArchived()`。
只有创建者能归档/取消归档，重复归档幂等（不涨版本号）。

错误码选 409 而不是 403 是有意的：403 的意思是「你没权限」，会让前端提示「请联系创建者开通权限」，
而真实原因是「这个行程已经结束、整体锁了」。所以专门开了 `ItineraryArchivedException`，
响应体带 `archived: true`，让前端能直接给出「取消归档后可继续编辑」的引导。

列表接口加 `?archived=true|false` 过滤，**默认两边都返回**——悄悄把归档行程藏起来，
用户会以为数据丢了。

### 5. 导出：纯文本，不动用户磁盘

`ExportService.toText()` 渲染成员、方案、每日安排、交通、住宿、费用（含小计与分类）、
预算分析、候选与投票、行程检查、免责说明。选纯文本而不是 PDF/Word：没有字体与分页依赖，
任何编辑器都能打开，也方便直接贴进群聊。文件名走 `ContentDisposition.attachment().filename(name, UTF_8)`，
中文名不会乱码。**服务端不往用户磁盘写任何东西**，只把字节流回给客户端。

### 6. 兼容旧数据

`Itinerary`、`Plan`、`Expense` 都新增了字段。为了不破坏已有 `data/*.json`，三个 record 各保留了一个
旧签名的重载构造器，旧 JSON 反序列化时新字段取默认值（`archived=false`、`budgetLimit=null`、`actual=false`）。
**不需要迁移脚本，也不需要手改数据文件。**
