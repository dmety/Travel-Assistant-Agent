### 2.3 真实服务回归覆盖到的业务链路

`tools/acceptance.py` 用随机端口与临时数据目录启动打包后的 JAR，覆盖：

- 注册、重复注册 409、错误密码 401、登录、登出后会话失效
- **并发重复注册：恰好一个 201、一个 409**
- 创建行程 → 依次更新方案/交通/住宿/每日安排/费用五个板块，版本 1→6 连续递增
- 子项 id 自动补全、五大板块均落库
- 邀请成员 → 成员可查看 → 有板块权限可改（改签生效）→ 无板块权限返回 403 且版本不变
- 过期版本提交返回 409，响应头 `X-Version` 带回最新版本
- 费用为负 400、离店早于入住 400、邀请未注册用户 400、标题空白 400、修改不存在成员 404
- 密码以 BCrypt 落盘（`$2` 前缀）
- **进程真实重启**后账号与行程均可读，删除后重启仍不存在

其中 409 / 403 / 400 / 404 四类边界与本轮之前提出的六条缺陷一一对应，属既有缺陷的回归证据。

## 六、问题与处理

### 6.1 旧索引的核验状态是虚标的（本轮最重要的发现）

主干重建了 `data/attractions_index.json`，5731 条记录发生变化。逐条比对后确认：

| 字段 | 旧索引（本轮同步前） | 新索引 |
| --- | --- | --- |
| `ticket_status = verified` | 752 条 | 0 条 |
| `open_time_status = verified` | 4628 条 | 0 条 |

而源库 `data/china_attractions.json`（同步前后**内容完全未变**）里根本不存在 `verified`：`ticket_status` 只有 pending 11048 / unverified 810，`open_time_status` 只有 pending 7205 / unverified 4653。

也就是说，旧索引里的 5380 条「已核验」与自己的源库矛盾，是索引过期造成的虚假标注，而不是源数据被降级。新索引把状态归零后才与源库对齐。

处理：主干给 `build_attraction_index.py` 增加了 `--check` 模式，索引与源库不一致即返回退出码 5，并把该检查接进 README 的三步验收入口。这条从机制上堵住了复发。

**对我的影响**：此前日志中若引用过「票价已核验」这类表述，应一律以新状态为准，即当前**没有任何一条景点的票价或开放时间被标记为已核验**。字段有值不等于已核验，未知费用不能当免费。
