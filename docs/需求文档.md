## 1. 项目目标

为结伴出游的学生做一个行程规划工具。用户用自然语言描述出行需求，系统生成带来源的草案；邀请其他账号在不同电脑上共同编辑；系统核算预算、校验时间，重启后恢复数据。

11-09 起目标扩展了一条：用户不必填表，可以直接用对话的方式提问和修改，模型自己去查数据。

## 2. 用户与权限

- 未登录用户：注册、登录，可以查看景点与购票信息。
- 创建者：创建、查看、编辑、删除自己的行程，邀请或移除成员。
- 成员：接受邀请后查看、编辑共享行程，可退出；不能删除行程或管理成员。
- 服务端必须验证每次请求的身份和行程权限，不能依赖客户端隐藏菜单。

## 3. 业务流程

填表路径：注册登录 → 输入自然语言需求 → Agent 补问缺失信息并生成草案 → 用户修改确认 → 保存行程 → 邀请成员 → 成员接受并编辑 → 查看预算与校验结果。

对话路径：注册登录 → 打开对话页 → 提问（「下周六带爸妈去武当山玩四天，预算六千」）→ 系统解析意图与槽位 → 模型决定查哪些工具 → 回答并给出可点选的下一步。

两条路径共用同一套行程、权限与保存逻辑。对话只是入口不同。

## 4. 功能需求

### 4.1 V1：基础协作规划

- 账号注册、登录；创建者邀请已注册用户，受邀者接受或拒绝。
- 检索本地景点快照后生成带来源的草案，用户确认后保存。未知价格和开放时间要明确标记，费用未知不按零元处理。
- 支持多条行程的创建、查看、编辑、删除；区分短途周末游和长途跨省游，记录成员、交通、住宿、景点和预计费用。
- 汇总已填写的非负费用，缺失费用标记为待填写；返回时间不得早于出发时间。
- 两名成员同时编辑时检查版本，冲突时拒绝覆盖并提示重新读取。
- 服务端以本地文本文件持久化账号、邀请和行程，重启后恢复。

### 4.2 V2：查询与完善

- 查询地点、天气、步行、驾车和公交路线；显示来源及查询时间。
- Agent 结合查询结果提出行程调整，用户确认后保存。
- 检查各安排的时间范围及重叠。结束早于开始禁止保存，重叠只提示确认。
- 提供成员留言、修改记录和分类预算。
- 票务辅助：提供经核验的官方入口与已查询规则，显示来源和时间。未接入库存接口时显示「余票未核验」，无可靠入口时提示自行进入官方渠道。

### 4.3 V3：决策与总结

- 成员添加候选地点并投票，用户决定最终选择。
- 记录预算上限和实际支出，展示预计、实际、差额和人均费用。
- Agent 结合现有数据提示风险并解释建议，用户确认后应用。
- 导出可阅读文本摘要，归档已结束行程。

### 4.4 V3 之后增补：对话式交互

这一节的需求在 11-09 至 11-10 落地，原需求文档没有。

- **一句话解析**：用户说一句完整的话，系统拆出目的地、天数、人数、预算、偏好五个槽位。前端不做正则匹配。
- **地名归属**：用户说的地名可能是不在知识库里的县级地名。系统要判断它属于哪个城市，查不到就转实时检索，不能直接把问题丢回给用户。
- **对话回答**：模型看着工具清单自己决定查什么，查完再回答。工具至少覆盖景点检索、天气、餐饮、行程草案、购票建议、灵感候选、投票。
- **上下文记忆**：同一会话内，用户说「那说一下武汉」时能接上上一轮的语境。
- **对话不改数据**：对话只出建议，落库必须经用户确认。模型不能直接写文件。
- **可点选补问**：缺信息时给可选项，不让用户重打一遍。
- **降级要说清**：模型不可用时，如实说明降级原因，不假装查过。

### 4.5 运维增补：管理后台与令牌门禁（11-13 至 11-14 落地）

这一节同样不在原需求里，属开发侧为「能查、能管、能审计」补的运维面。

- **管理后台**：`/admin` 提供 Provider 注册表与准入（探测 / 影子 / 启用）、能力状态、意图路由、模型用量、操作审计、令牌管理。
- **令牌单因子门禁**：管理端点（`/api/agent/providers*`、`/api/agent/metrics/model-usage`、`/api/agent/audit-log`）不再依赖登录会话，只认 `X-Admin-Token`；令牌经环境变量注入，未配置时一律 403（fail-closed），比对用常量时间。
- **浏览器端密钥分离**：百度 AK 分服务端 WebAPI key 与浏览器端 AK 两把，`/api/map/config` 只下发浏览器端那把，且要求登录；未配置时前端回落示意底图。
- **审计与用量只读**：用量是本进程累计快照，不含账户余额；审计按时间倒序，`limit` 夹在 1～500。

### 4.6 未纳入范围

- 景区正式票务履约：真实景区库存锁定、签发可入园门票，以及与景区供应商之间的正式订单和退改接入。§4.6.2 的演示订单与模拟票不代表此类正式履约。
- 酒店预订。
- 实时余票保证。
- 美食 Agent 的独立部署。

### 4.6 新增需求（代码实现状态）

> 本轮已完成下列功能的代码实现；尚未运行本轮测试或进行团队正式验收。真实支付、正式景区出票和实时停车位不在已实现能力内，使用边界见 [CLI 使用文档](CLI使用文档.md)。

#### 4.6.1 CLI 作为并列操作入口

- CLI 与现有 Web 前端、移动端并存，实现三端。
- 项目已有功能均应能通过 CLI 操作；新购票和停车能力也提供 CLI 入口。
- CLI 通过服务端接口执行业务操作，并沿用服务端身份认证、权限与校验，不在客户端复制业务规则或直接读写服务端数据文件。
- 新增或调整服务端接口须保持向后兼容。现有 Web 前端与移动端的页面、交互和既有请求行为不因 CLI 开发而改变。
- 复用现有 JLine 终端能力，统一帮助信息、命令层级、中文对齐、状态提示和表格呈现；支持交互式演示及可重复执行的命令。

#### 4.6.2 演示购票交易闭环

- CLI 创建演示订单并展示二维码。当前没有支付平台 SDK、合规商户配置、授权测试收款账户或凭据，因此只启用沙箱，不会尝试真实收款。
- 支付服务提供 `PaymentGateway` 适配边界，可用 `TRAVEL_PAYMENT_PROVIDER` 选择 Spring 注册的适配器；当前只提供 `sandbox` 实现且只接受 `TRAVEL_PAYMENT_MODE=sandbox`。未来真实适配器的凭据须通过仓库外的安全配置注入，不得写入仓库、日志或演示清单。
- 沙箱确认只核对订单金额与 CNY 币种，并以订单所有者会话授权；重复确认不会重复出票。当前没有支付平台通知、外部回调验签、查单或商户结算能力，不能声称已验证真实支付。
- 已评估当前 JSON Store：仅支持单进程内同步和单文件原子替换，不支持多实例并发写入、跨进程一致性或真实交易对账/恢复，不能用于真实收款。
- 当前沙箱 Provider 在服务端模拟支付确认后自动签发演示票，不增加供应商侧 CLI 或人工出票步骤。CLI 可查询订单状态、支付状态与出票结果。
- 演示票必须显著标注「演示票」。真实景区供应商适配接口可以后续接入；模拟出票不得描述成景区正式出票，也不得暗示可凭此入园。
- 沙箱代码路径支持订单查询、15 分钟惰性超时、模拟支付失败、重复确认幂等、取消与模拟退款。真实支付退款、支付失败回调和供应商出票失败仍需未来适配器处理，当前不报告为已打通。

#### 4.6.3 自驾与停车场

- 出行方式按行程路段选择，支持自驾；现有步行、公交等方式继续可用。
- 自驾路段展示驾车路线，并查询目的地附近停车场；停车场结果可从 CLI 查看。
- 停车场 POI 名称、位置和距离附带高德来源及查询时间。当前接口不提供可靠价格、营业时间与实时车位，均返回「未知」且标明无实时空位数据。
- 停车数据源不可用时说明降级原因，不影响既有行程读取与编辑。

## 5. 非功能需求与边界

- 多客户端须连同一个可访问服务；网络中断时无法共享编辑。
- 密码用成熟哈希算法保存；密钥通过环境变量配置，不进仓库。
- 外部 API 超时、失败或数据不足时说明原因；既有行程仍可查看和编辑。
- 知识库字段必须区分「未知」与「已核验」，标记来源、时间及坐标系。发布融合库前核对数据许可，免费额度不等于分发授权。
- 单个进程串行写入。不支持多个实例同时写同一份文件。数据文件需定期备份。

## 6. 验收

**V1**：两台电脑完成注册、生成、邀请、编辑、冲突检查和重启恢复。另验证景点 ID 与证据可追溯、未知费用披露、检索失败和有限修订。

**V2**：验证地图查询、工具调用、时间冲突和修改记录。另验证购票入口、规则来源、库存未知及无可靠入口提示。

**V3**：验证投票、预算分析、建议确认、导出归档。要覆盖无权限访问、无效输入、外部接口失败和文件读写失败。

**对话能力**（11-10 起）：验证一句话解析出五个槽位、县级地名归位、会话内追问能接上语境、模型不可用时如实降级、对话不产生未确认的写入。

自动化验证（2026-11-12）：`mvn verify` 693 个测试通过，0 失败、0 错误、0 跳过；`tools/acceptance.py` 真实服务回归通过，含配置式本地模拟助手准入、调用与失败回退。静态测试数量不作为人工页面验收或真实外部接口成功的证明。截至 2026-11-15，`origin/main` 的用例总数已是 717（100 个测试类），新增 24 个用例尚未在文档侧重跑 `mvn verify`。

**本轮实现状态（未验收）**：CLI 通过专用命令和通用 `/api/...` 请求入口操作现有 REST 能力；新增沙箱订单、模拟支付确认/失败、自动演示出票、订单查询、15 分钟超时、取消与模拟退款；新增按地名自驾路段和周边停车 POI 接口。现有 Web 与移动端没有页面改造，原 API 路径与行为保留。本轮未运行测试，不能据此声称上述流程已通过自动化或人工验收。真实支付和景区正式票务仍需外部授权、供应商适配及更强的交易存储。
