## 三、缺陷清单

### T-2（P1）改了表单后草案不失效，保存进去的是旧日期

**现象**：生成草案后修改表单条件，确认按钮仍然可点，保存下去的是**生成草案时**的日期，界面上没有任何「草案已过期」的提示。

**复现（浏览器实测）**：

1. 填杭州、11-20 至 11-22、3 天，点「生成草案」
2. 把界面上的日期改成 12-01 至 12-03（输入框已显示新日期）
3. 点「② 确认保存为行程」

结果：提示「已确认保存」，但落盘的逐日安排是 `2026-11-20 / 11-21 / 11-22`，与界面显示的 12-01~12-03 不符。

**根因**：

`static/index.html` 第 1335~1340 行，确认按钮的启用条件只看草案里的问题项，不看当前表单值：

```js
function dfUpdateConfirmButton() {
  const questions = (currentDraft && currentDraft.questions) || [];
  const blocking = questions.filter(q => q.field === 'departDate' || q.field === 'returnDate');
  $('dfConfirmBtn').disabled = !currentDraft || blocking.length > 0;
  ...
}
```

而 `dfConfirmBtn` 的点击处理用的是 `currentDraftRequest`（生成草案时冻结的那份），输入框没有 `input` 监听去重置草案。

**影响**：用户改了出行日期但直接点保存，行程会按旧日期生成每日安排。用户要到查看行程时才发现日期不对，属于静默的数据不一致。

**建议修法**（二选一，都很小）：

- 给草案表单的所有输入加 `input` 监听：任一变化就把 `currentDraft` / `currentDraftRequest` 置空，调用 `dfUpdateConfirmButton()` 禁用按钮，并提示「表单已修改，请重新生成草案」
- 或者在 `dfUpdateConfirmButton()` 里比较当前表单值与 `currentDraftRequest`，不一致即禁用

**为什么不判 P2**：与 D-3（改不存在成员静默成功，但数据没变）不同，这条会让用户拿到**内容错误**的行程，且没有任何报错。
