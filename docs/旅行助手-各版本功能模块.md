# 旅行助手：各版本功能模块

## 版本说明

2026-11-04 更新：**V1 五节、V2 四块能力与 V3 四节均已落地**，共 232 个自动化用例全绿。
本文描述目标功能，已实现的条目在标题后标注状态；未标注的仍属规划。具体职责与边界见[专项方案](多Agent与票务能力方案.md)。

项目采用 V1 → V2 → V3 的递进方式开发。每个版本都是完整、可使用的产品；后续版本保留前一版本的功能，并在此基础上增加新能力。

用户在不同电脑上使用控制台客户端，连接同一个服务。服务统一管理账号和旅行方案，数据保存为服务端本地文本文件。

## V1：基础协作规划

### 1. 用户与账号

- 注册账号、登录和查看个人信息。
- 通过账号识别用户，访问方案时检查其身份和权限。

### 2. Agent 智能规划

- 用户用自然语言描述目的地、出行时间、预算和偏好等需求。
- Agent 提取需求；必要信息不足时向用户追问。
- Java 编排需求理解、景点推荐、行程规划三个 Agent，检索本地景点快照后生成含来源和未知项的草案。先完成单 Agent 基线，再验证角色拆分效果。
- 用户查看、修改并确认草案，确认后保存为正式方案。
- 对价格、开放时间等未经核实的信息给予提示。V1 暂不依赖高德实时查询。

### 3. 旅行方案管理

- 创建、查看、修改和删除多条方案。
- 记录目的地、出发和返回时间、成员、交通、住宿、景点和费用。
- 区分短途周末游与长途跨省游。
- 方案创建者可以删除方案；已加入的成员可以查看和编辑。

### 4. 邀请与多人协作

- 创建者按账号邀请其他用户；受邀者登录后接受或拒绝。
- 接受邀请后，成员可在不同电脑查看和编辑同一方案。
- 创建者可移除成员；成员可主动退出。
- 同时编辑时检查方案版本，发生冲突则提示重新读取，避免直接覆盖他人的修改。

### 5. 预算与时间检查

- 记录交通、住宿、景点等预计费用，自动汇总旅行总预算。
- 检查费用是否为非负数；未填写费用标记为待填写。
- 检查返回时间是否早于出发时间，并提示缺失或无效输入。

### 6. 数据保存与恢复

- 服务端将账号、邀请和方案等数据保存为本地文本文件。
- 服务重启后读取历史数据；用户登录后可继续查看和编辑。
- 文件读取或保存失败时提示用户，不静默覆盖原数据。

**V1 验收**：两名用户在不同电脑登录；一人通过自然语言生成并保存方案，邀请另一人加入并编辑；核对预算、时间检查、编辑冲突和重启后的数据恢复。

## V2：信息查询与行程完善

在保留 V1 全部功能的基础上，新增以下模块和能力。

### 1. 高德信息查询（已实现，需配置 `AMAP_KEY`）

- 根据城市和关键词查询景点或其他地点。
- 查询目的地天气。
- 查询两个地点之间的步行、驾车或公交路线，展示距离、预计时间和主要路线信息。
- 展示查询来源和时间；接口不可用或结果不足时明确提示。

> 未配置密钥时接口返回 503 并说明「哪些功能受影响、哪些不受影响」，**不返回 200 + 空结果**——
> 那会被理解成「当地没有这个地方」。天气按 adcode 查询，传城市名时先走地理编码解析，
> 解析不到直接报错，不拿猜的代码去查。

### 2. Agent 工具调用与调整（已实现基础版）

- Agent 根据用户需求选择并调用景点、天气或路线查询工具。
- 基于查询结果生成或调整行程草案，说明建议所依据的信息。
- 用户确认后才将建议保存到正式方案。

> 工具选择由 **Java 显式编排**（景点 → 天气 → 票务），模型只负责组织语言。这样每条建议都能
> 追溯到来源，不会出现「没查就答」。模型未配置时仍返回带 ID 与来源的候选清单，只是没有文字建议。
> 「用户确认后才保存」由接口形态保证：`/api/agent/plan` 不写库。
> **未做**多轮补问对话与自动修订——当前是一次请求出一份草案。

### 3. 详细时间检查（已实现）

- 为交通、住宿和景点安排记录开始和结束时间。
- 检查结束早于开始、安排超出旅行时间范围等无效情况。
- 对安排时间重叠给出提示，由用户检查并决定是否调整。

> 只有「结束早于开始」在写入时拦截（纯笔误，没有合理解释）。重叠与越界只做体检提示，
> 因为服务端直接拒绝会挡掉正在编辑的中间状态（例如正在调换上下午顺序）。
> 重叠用扫描线找「与当前最晚结束项相交」的对，既不会漏报，也不会把互相重叠的 n 项展开成 n² 条提示。

### 票务 Agent：购票辅助（已实现辅助部分，不含交易）

- 提供经核验的官方购票入口、已查询票种与规则，展示来源和查询时间；用户跳转完成购买。
- 无库存接口时显示“余票未核验”；无可靠入口时提示自行进入景区官方渠道。
- 正式接入场次后与规划 Agent 协作调整时间；不得自行替用户购买替代产品。

> 入口来自人工维护的白名单配置（`ticket_channels.json`），**默认不存在**。系统不抓取、不推断、
> 不生成任何链接；`stockVerified` 恒为 `false`。场次协作与下单/支付/出票不在本阶段范围。

### 4. 协作记录与留言（已实现）

- 记录方案的修改人、修改时间和修改内容。
- 成员可以留言讨论，并查看方案的修改记录。

> 两者都是旁路数据，**不改变行程版本号**——讨论不该把人挤进 409。
> 修改记录只由服务端在写操作成功后产生，`actor` 取会话身份，客户端无法伪造。

### 5. 分类预算（V1 已实现）

- 按交通、住宿、景点等类别展示预计费用。
- 汇总各类别费用和旅行总预算。

**V2 验收**：成员新增景点后让 Agent 查询路线并提出建议，用户确认修改；检查时间冲突、留言、修改记录和外部接口失败提示。

> 当前验收状态：时间冲突、留言、修改记录、外部接口失败提示均可复现（见[测试说明](测试说明.md)）；
> 「让 Agent 查询路线并提出建议」这一条需配置 `AMAP_KEY` 与 `DEEPSEEK_API_KEY` 才能实测，
> 未配置时只验证了解析逻辑与降级路径，未做真实联调。

## V3：团队决策与总结

在保留 V1、V2 全部功能的基础上，新增以下模块和能力。

### 1. 候选地点与投票（已实现）

- 成员添加景点或住宿候选项。
- 成员对候选项投票并查看结果，由用户决定最终选择。

> 任何能查看行程的人都能提候选、投票，不需要板块编辑权——提候选是提议，不是改方案。
> 同一人对同一候选只保留一张票，再次投票是改票而非加票；排序按净支持（支持 − 反对），
> 因为「3 支持 2 反对」和「4 支持 4 反对」不是一回事。**平票不给赢家**：`leaderId` 为空并说明原因，
> 系统没有资格用「谁先提的」替一群人做决定。候选与选票独立落盘，**不推动行程版本号**；
> 只有「确认加入」才写入每日安排，并要求 DAILY 编辑权与当前版本号。

### 2. 预算分析（已实现）

- 记录预算上限及各项实际支出。
- 展示预计总额、实际总额、与预算上限的差额，以及按成员人数计算的人均费用。
- 提示预算超支或预计超支。

> 「实际支出」用费用上的 `actual` 显式标记，而不是靠「日期早于今天」去猜——补录的旧票据和
> 提前写下的预算，日期看起来可能完全一样。上限为空就说「未设定」，不拿 0 冒充（0 意味着「一分不花」）。
> 上限币种与费用主币种不一致时**不换算也不硬减**，`comparable=false`、差额为空并说明原因。

### 3. Agent 综合决策建议（已实现基础版）

- 综合已有的成员投票、预算、天气和路线信息，提示潜在风险并说明建议依据。
- 提供可供讨论的调整方案；用户确认后才修改正式行程。

> 风险与建议由 **Java 规则**算出（预算超支、投票并列、时间重叠、交通到达晚于当天安排、
> 多晚行程无住宿、旅行日期内有雨雪），每条都带 `severity` 与 `basis`（依据哪类数据）；
> 模型只负责把这些事实组织成文字，未配置时 `advice` 为空但结论照常完整。
> 「路线信息」当前取自行程里已登记的交通，不新增外部路线调用。

### 4. 行程导出与归档（已实现）

- 将行程、成员、路线和预算导出为可阅读的文本摘要。
- 将已结束的旅行方案归档，并允许用户查看归档方案。

> 导出为**纯文本**：没有字体与分页依赖，任何编辑器都能打开，也便于贴进群聊；服务端不写用户磁盘。
> 归档后**所有**写入口（五大板块、成员、候选投票）一律返回 409，只有创建者能归档/取消归档；
> 重复归档幂等，不涨版本号。归档不删除数据，列表可按 `archived` 过滤，默认两边都返回。

**V3 验收**：成员添加候选地点并投票；Agent 结合已有信息给出建议；用户确认方案、记录支出、导出摘要并归档，重启后数据仍可读取。

## 实现边界

- 保留单体与三 Maven 模块，使用 Spring AI 加 Java 显式编排，初期不增加多 Agent 框架。Python 离线构建、Java 在线检索。
- 完整下单、支付跳转、出票和退改为 V3 之后的条件性扩展；平台授权、接口和订单持久化方案明确后实施，不计入当前 V3 验收。

- 跨电脑协作需要共享服务持续运行，且客户端能够通过网络访问该服务；数据保存在服务端本地，而不是各客户端独立保存。
- DeepSeek 用于理解需求和生成建议；V2 起高德提供地点、天气和路线查询。具体接口权限、额度和费用需在接入前核实。
- Agent 建议由用户确认；外部查询失败时应说明原因，已有方案的查看与编辑仍应可用。
