## 二、T-1（P2）游客为空时合计显示 0 元

### 现象

填了景点和日期、但还没添加任何游客时，接口返回 `estimatedTotal = 0`，前端据此渲染「门票估算：0 元」；**同一个响应里又在追问「请添加每位游客」**，两处自相矛盾。

游客列表为空本该是「还算不出来」，结果给了一个确定的 0 元。

### 复现

```bash
curl -s --noproxy '*' -X POST http://127.0.0.1:8080/api/agent/tickets/advice \
  -H 'Content-Type: application/json' \
  -d '{"message":"","needs":{"attraction":"八达岭长城","date":"2026-11-10","product":"STANDARD","visitors":[]}}'
```

实际返回（节选）：

```json
{
  "questions": ["请添加每位游客（无需姓名、证件号）"],
  "matches": [],
  "estimatedTotal": 0
}
```

`ticket-assistant.html` 第 468~470 行据此渲染：

```js
"门票估算：" + (r.estimatedTotal == null ? "未知／资料不全" : r.estimatedTotal + " 元")
```

于是页面上同时出现「还需要确认：请添加每位游客」和「门票估算：0 元」。

### 根因

`travel-server/src/main/java/com/travelassistant/server/application/ticket/TicketAssistantService.java` 第 138~140 行：

```java
      boolean inRange = site.fields().values().stream().allMatch(f -> dateInRange(selectedDate,f));
      if (inRange && visitors != null && date != null) {
        total = BigDecimal.ZERO;
        for (int i=0;i<visitors.size();i++) { ... }
      }
```

空列表满足 `visitors != null`，于是进入分支，`total` 被初始化为 0；循环一次都不执行，`total` 就以 0 收场。

对比同一方法里的单价处理：票价缺失时 `price` 返回 `null`，`total` 随后被置空——**单价是「未知」，合计却成了「免费」**，同一份响应里两套语义。

### 修复

第 138 行加一个空列表判断即可：

```java
      if (inRange && visitors != null && !visitors.isEmpty() && date != null) {
```

改完 `total` 保持 `null`，前端自动走「未知／资料不全」分支，不需要改页面。

**副作用已验证**：按上面改这一行后跑全量，`Tests run: 348, Failures: 0, Errors: 0, Skipped: 0`，没有既有用例依赖「空游客得 0」这个行为。

### 验收

1. 删除 `TicketAssistantTest.emptyVisitorsMeansUnknownTotalNotZero` 上的 `@Disabled`
2. 跑 `mvn -B test -Dtest=TicketAssistantTest`
3. 该用例通过即算修好，**跑一次就够，不需要重复跑**

这条断言的写法是先要求有追问、再要求合计为 `null`：

```java
    Needs n = new Needs("八达岭长城", LocalDate.parse("2026-11-21"), "STANDARD", List.of(), null, null);
    Result r = advise(n);
    assertThat(r.questions()).anyMatch(q -> q.contains("游客"));
    assertThat(r.estimatedTotal()).isNull();
```

**我做过反向验证**：不改代码、只删掉 `@Disabled`，该用例稳定失败，报 `expected: null`（实际 0）。它不是摆设。加上那一行修复后立即转绿。

### 不建议的做法

- **不要在前端把 0 显示成「未知」**。数据层就该是 `null`，否则其他调用方（客户端、导出）仍然拿到 0，问题只是被页面挡住了一次。
- **不要在游客为空时返回 400**。缺游客是正常交互的中间态，用户下一步就会补，返回错误会让页面走到异常分支，把可继续的追问变成报错。
- **不要把 `matches` 里塞占位价格来凑合计**。合计与明细必须对得上，否则又变成另一种口径不一致。

### 同类风险（建议顺手看一眼）

如果其他地方也用 `集合 != null` 判断集合非空，可能有同样的「空集合被当成有效输入 → 得到 0 或空结果」问题。这轮只在这一处确认了实际影响，没有全库排查。
