第 4 步修了两处**产品缺陷**（都是测试先发现的）：

1. **权限必须先于归档**。`requireEdit` 原来先 `requireNotArchived` 再判权限，于是非成员对一份已归档行程
   提交修改会拿到 409 + `archived:true`——状态码虽然也是「拒绝」，但那等于告诉一个无权查看的人
   「这个 id 存在，而且已经定稿」。改成权限先命中后，五条写路径对非成员统一 403，响应体里没有 `archived`；
   `leave` 同理，非成员退出已归档行程改为 404「成员不存在」。代价是「有权限但没给这个板块」的人
   拿到 403 而不是 409——他有查看权，本来就知道行程状态，不构成额外泄露。
2. **`ItineraryStore` 先落盘再更新内存**。原来 `save` 先改内存副本再写文件，写失败（目录被删、磁盘满、
   杀软锁文件）时异常照常抛给调用方，但内存里已经有了这条行程：刷新还在、重启就没了。
   这种「失败但看起来成功」比直接失败更难解释。改完之后 T-09 才成立——
   **顺手回退该修复验证过：用例立刻变红**，说明它不是摆设。

T-11 刻意**不做时间断言**。分片锁的收益是「不同行程不排队」，但单次写入只有几毫秒，
在共享机器上「并行比串行快」的阈值随时会被 GC 和磁盘抖动吃掉，写时间比较必然 flaky。
能稳定验证的是数据不串：八个行程并发写各自方案，版本各自前进一步、summary 各自正确。
如果锁的键算错或共享了可变状态，这里立刻显形。

### 2.2 六个结构性问题（P-1 ~ P-6）

**P-1 基线不绿，且是 flaky。**（以下为改造前实测）
`mvn -o -pl travel-server -am test` → `Tests run: 242, Failures: 1`：
`CollaborationApiTest.changelogRecordsWritesInReverseOrder` 断言 `log[0].section == "PLAN"`，实际拿到 `ITINERARY`。
**单跑该类 8/8 通过**，全量跑必挂 —— 典型顺序/负载敏感。

根因不在测试，在产品代码。`CollaborationStore.findChanges`：

```java
.sorted(Comparator.comparing(ChangeEntry::at).reversed())
```

`Instant.now()` 在本机存在时钟粒度，同一次请求内「创建行程」与「更新方案」两条记录拿到了**完全相同**的时间戳。实测本次运行的数据文件，175 条记录里有 **20 组**同行程 `at` 重复：

```text
06:06:04.263229300Z  ITINERARY  v1
06:06:04.263229300Z  PLAN       v2
```

`sorted()` 是稳定排序，`reversed()` 不会把相等元素反过来，于是创建记录仍排在最前。全量跑时机器更忙，两次 `now()` 更容易落在同一刻度，命中率随之升高。

修复（`version` 是天然单调的 tie-breaker）：

```java
private static final Comparator<ChangeEntry> NEWEST_FIRST =
    Comparator.comparing(ChangeEntry::at).thenComparingLong(ChangeEntry::version).reversed();
```

`addChange()` 里裁剪最旧记录的排序也要加同样的 tie-breaker，否则「丢哪条」同样不确定。

**已修复**：`CollaborationStore` 定义 `OLDEST_FIRST = comparing(at).thenComparingLong(version)`，
`findChanges` 用 `OLDEST_FIRST.reversed()`，`addChange` 裁剪用 `OLDEST_FIRST`。
修复后 `mvn test` 连续 5 轮 241 / 0 失败，该用例不再靠时钟运气。

**P-2 时间敏感断言没有可注入的时间源。**
`ChangeEntry.of` 直接 `Instant.now()`，测试无法构造「同一时刻两条记录」的确定性场景。
建议 `ChangeLogRecorder` 接受 `Clock`（默认 `Clock.systemUTC()`），测试注入 `Clock.fixed(...)`。这是把 flaky 变成确定性断言的标准做法，收益高于任何重试机制。

**P-3 测试数据写在 C 盘且不回收。**
改造前有 **7 处**各自调用 `Files.createTempDirectory(...)`：`ApiTestBase`、`V2ApiTestBase`、
`AttractionTestBase`、`AttractionCorruptTest`、`AttractionMissingTest`、`OptimisticLockConcurrencyTest`、
`OptimisticLockStressTest`（`OptimisticLockAtomicityTest` 另有一处）。全部落在 `%TEMP%`，进程退出不删除。
实测本机累积 **58 个目录 / 2.1 MB**。持续跑 CI 会线性增长，且与「产物不进 C 盘」的约定冲突。

**已修复**：新增 `TestDataDirs`，统一落 `target/test-data/<pid>-<nano>/<用途>`，注册 shutdown hook 递归删除。
跑完 `target/test-data` 残留 0、C 盘新增 0；历史 49 个目录已清理。`mvn clean` 亦可兜底。

**P-4 断言依赖全局顺序。**
`ItineraryIntegrationTest` 断言 `$[0].id`，`list` 返回顺序取决于 `store.findAll()` 的数组顺序与用户名生成时机。共享数据目录下，任何新增用例都可能改变顺序。
**已修复**：改为 `jsonPath("$[*].id", hasItem(id))`。

**P-5 纯逻辑没有独立单元测试（覆盖率不低，但耦合在 HTTP 层）。**
`BudgetCalculator`（415 行、3 个 static 方法，含多币种、人均分摊、除零、金额 scale）**没有任何直接单测**，
只通过 `GET /budget` 间接覆盖；`DailyActivity.timeInverted()`、`Itinerary.withXxx()` 的版本递增语义、
`ExportService.render` 的文本拼装同样没有。

接入 jacoco 后这个判断需要修正：`BudgetCalculator` 实测行 **92.8 %** / 分支 **80.1 %**，被
`BudgetAnalysisTest` 与 `ItineraryBudgetTest` 走得很透。真正低的是 `ExportService`（行 68.4 % / 分支 **40.5 %**）。
所以补单测的理由不是「没覆盖」，而是形态问题：所有断言都挂在接口返回的 JSON 上，
一个分支算错只表现为「某个字段不对」，得先怀疑聚合逻辑、再怀疑序列化、再怀疑权限——定位链路长。
单测能把「算术错」和「接线错」分开。

**P-6 无 Web 层切片，无 IT 分层，无覆盖率。**
改造前 pom 里只有 `spring-boot-starter-test` + `spring-security-test`：没有 jacoco、没有 failsafe、没有 surefire 的 `*IT` 约定。后果是 `mvn test` 与 `mvn verify` 等价，慢测试无法隔离；参数绑定、响应头、异常映射这些**只依赖 Web 层**的契约，必须拉起整个容器才能验证。

**已修复**：jacoco 0.8.12、surefire 排除 `*IT`/`*StressTest`、failsafe 接管 `*IT` 已接入，
压力观察类不再出现在「跳过」里（315 用例 / 0 跳过）；Web 层切片由 `ItineraryControllerTest`
（`@WebMvcTest`）补上，参数绑定与响应头不再需要拉起整台容器。

## 3. 分层策略

| 层 | 技术 | 测什么 | 不测什么 | 替身 | 耗时/用例 | 归属 |
|---|---|---|---|---|---|---|
| **L1 单元** | JUnit 5 + AssertJ + Mockito，**不加载 Spring** | 纯函数与领域不变式：金额聚合、时间比较、版本递增、id 补全、导出文本 | HTTP 状态码、序列化、权限链 | 手写假实现或 Mockito | < 5 ms | `domain/`、`application/` |
| **L2 Web 切片** | `@WebMvcTest` + `@MockitoBean`，或 `MockMvcBuilders.standaloneSetup` | 参数绑定、`@Valid`、`X-Version`、错误体形状、`Content-Disposition` 编码 | 业务规则、持久化 | Service 全部 mock | 100–300 ms | `interfaces/rest/` |
| **L3 集成** | `@SpringBootTest` + `MockMvc`（现状主力） | 权限 × 版本 × 板块的组合、异常到状态码的映射、落盘与重启、并发原子性 | 纯计算细节（已由 L1 覆盖） | 无（真实磁盘，`target/test-data`） | 30–200 ms | 跨层契约 |
| **L4 端到端** | 真 HTTP（`examples/itinerary_usecase_hangzhou.py`）+ 浏览器冒烟 | 真实网络栈、Cookie 会话、静态页与接口联通、跨角色完整剧本 | 分支细节 | 独立进程 + 临时数据目录 | 3–10 s | 发布前 |

**分配原则**：同一个规则只在一层断言。权限矩阵放在 L3（要真实 Security 链），金额聚合放在 L1（不该为算术拉起容器），错误优先级矩阵放在 L2+L3 各测一半。

**关于「切片有多快」的实测修正**：得看是不是冷启动，两个数字差别很大。

| 场景 | `ItineraryControllerTest`（L2，5 条） | `ErrorPriorityTest`（L3，5 条） |
|---|---|---|
| 单独一个 JVM（冷启动） | 5.36 s | 7.17 s |
| 并在全量套件里（JVM 已热） | **1.54 s** | 1.20 s |

冷启动只省约 1.8 s，因为 `MockMvc` 的 web 上下文本身就要几秒；但套件内它只花 1.5 s，
比同规模的 L3 类还略高一点——说明**切片省的不是时间，而是依赖面**：不碰磁盘数据目录、
不加载账号与景点索引、不受其他用例写入的数据影响，因此可以放心重跑与将来并行。
把它当成「快 20 倍」的手段会失望；把它当成「让 Web 契约有独立、可重复的验证位置」才对。

**为什么不引入 Testcontainers / 契约测试框架**：当前持久化是文件，没有外部中间件；团队规模与迭代节奏不支持维护一套契约服务。等出现真实数据库或多客户端并行开发再引入。

## 6. 工程化改造

### 6.1 测试数据隔离（对应 P-3 / P-4）

```java
// ApiTestBase.java 调整
protected static final Path DATA_DIR = Path.of("target", "test-data",
    ApiTestBase.class.getSimpleName() + "-" + System.nanoTime()).toAbsolutePath();

@AfterAll
static void cleanData() throws IOException {
  // 删除本次运行产生的数据；失败不致命，但会打印告警
}
```

配套两条纪律：

1. 不再在断言里使用 `$[0]`，改 `jsonPath("$[*].id", hasItem(id))`；
2. 需要「全新状态」的用例（并发、持久化恢复）**不要复用容器**，像 `OptimisticLockAtomicityTest` 那样手工装配对象，成本反而更低。

### 6.2 pom 改造（对应 P-6）

```xml
<!-- travel-server/pom.xml -->
<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <executions>
    <execution><id>prepare-agent</id><goals><goal>prepare-agent</goal></goals></execution>
    <execution><id>report</id><phase>verify</phase><goals><goal>report</goal></goals></execution>
  </executions>
</plugin>
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <configuration>
    <excludes>
      <exclude>**/*IT.java</exclude>
      <exclude>**/*StressTest.java</exclude>
    </excludes>
  </configuration>
</plugin>
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-failsafe-plugin</artifactId>
  <configuration>
    <!-- jacoco 与 failsafe 同时用 argLine 时必须显式传递，否则覆盖率只统计 surefire -->
    <argLine>@{argLine}</argLine>
    <includes><include>**/*IT.java</include></includes>
  </configuration>
  <executions>
    <execution><goals><goal>integration-test</goal><goal>verify</goal></goals></execution>
  </executions>
</plugin>
```

版本由 `spring-boot-starter-parent` 统一管理，无需指定。

覆盖率门槛**先只报告不拦截**，跑满两周拿到真实基线后再开 `check`：

```xml
<execution>
  <id>check</id><phase>verify</phase><goals><goal>check</goal></goals>
  <configuration>
    <rules>
      <rule><element>BUNDLE</element>
        <limits><limit><counter>LINE</counter><value>COVERAGE</value><minimum>0.65</minimum></limit></limits>
      </rule>
    </rules>
  </configuration>
</execution>
```
