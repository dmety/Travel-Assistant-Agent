美食推荐（FOOD_RECOMMEND）

          

            
            
            
            
          

          

            
            
            
            
            
            
          

          

            
            
            
            
            
            
          

          

            美食按位置 proximity 检索，必须提供定位锚点：打开含坐标景点的行程（自动读取 attractionIds），或在上方填写经纬度（国内 POI 用 GCJ-02 最常用）。两者皆无时，后端按设计返回 REFUSED，不会默认使用城市中心。
          

          

            接口、半径与降级口径
            
走 POST /api/agent/invoke，intent=FOOD_RECOMMEND，需要登录。城市为必填；
            餐次、预算、忌口影响本地规则与（有密钥时）地图候选的生成。后端必须从带坐标系标签的锚点定位，不按城市中心兜底；
            留空经纬度又没打开含坐标行程时会返回 REFUSED（信封里能看到原因，这本身就是一种联调反馈）。下方结果来自契约信封，可直接核对 facts 与 evidence。

            
半径只支持 500 / 1000 / 3000 米三档，填其他值会就近取档，并在 notices 里写明实际生效值。
            忌口填「无 / 没有 / 不限」等同不限制，不会被当作关键记号。景区、山区等点位周边可能确实没有餐饮 POI，
            此时返回 DEGRADED + 零候选属正常（不编造），扩大半径或用西湖示例可对照验证。

          

          

          

        


        

          
多智能体方案投票（两轮范式 B）

          

            
            
          

          

            
            
          

          

            
            
          

          

            
          

          

            走 POST /api/agent/vote，需要登录。intent 固定为 DECISION_ADVICE（投票入口只接受这一个值）。
            第一轮 COLLECT 征集事实加候选（模型优先，无密钥走规则草案），
            第二轮 SCORE 由三位评委按独立 rubric 打分，PlanVoteTally 确定性计票。下方信封可直接核对 ranking、breakdown、excluded、rejections、notices。
