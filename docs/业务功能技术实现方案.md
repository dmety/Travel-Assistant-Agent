# 旅行助手业务功能技术实现方案

> 本文讲各业务功能怎么写。截至 `efc3e4a`（2026-11-10），V1、V2、V3 全部实现，
> 另有一批对话式能力在 V3 之后实现。接口细节以[接口文档](服务端REST接口文档.md)为准，
> 代码结构以[架构设计](架构设计.md)为准。
> 早期决策的取舍理由保留在每节末尾的「为什么这样选」，不再标注「实现口径」。

## 1. 账号与身份

服务端提供注册和登录接口，用户名唯一，密码用 BCrypt 哈希。登录后由 Spring Security 建会话，`JSESSIONID` 带 HttpOnly 与 SameSite=Strict。未认证请求返回 401，不跳登录页。

授权依据是当前用户与行程成员关系。成员被移除后，下一次请求就失效。令牌和密码不写日志。

为什么用服务端会话：客户端有 Java 控制台和浏览器两种形态，Cookie 方案两边都能用；JWT 需要在每个工具调用里传身份，容易漏。

## 2. 生成行程草案

**填表路径**。客户端提交自然语言需求，服务端调模型解析出目的地、时间、类型、预算和安排，校验字段后返回草案。缺字段时返回补充问题，不保存不完整结果。用户编辑确认后调行程接口保存。

**对话路径**（11-10）。`ChatAgent` 拿 8 个工具的清单请求模型，模型返回 `tool_calls`，Java 逐个校验参数、执行、回填结果，模型再组织语言。工具清单：

| 工具 | 作用 |
|---|---|
| `resolve_place` | 判断地名属于哪个城市 |
| `list_attractions` | 按城市查景点 |
| `get_weather` | 查天气 |
| `find_food` | 查附近餐饮 |
| `draft_itinerary` | 按城市和天数排行程 |
| `book_ticket` | 给购票建议与官方入口 |
| `get_inspiration` | 给灵感候选，支持库外实时检索 |
| `vote_plan` | 三评委两轮投票 |

**为什么改成交给模型选工具**：11-02 的方案是 Java 固定顺序（景点 → 天气 → 票务），好处是每条建议都能追溯，坏处是用户问「黄梅有什么好吃的」时链路走不通。11-10 改成模型自主选择，代价是要在提示词里写清边界（不许用常识补票价、没查到就转实时检索）。工具执行仍在 Java 侧，权限和参数校验没有放松。

## 3. 行程、费用与时间

行程分短途周末游和长途跨省游两类，交通、住宿、景点为安排对象。金额用 BigDecimal，时间用 `java.time`。总预算为已填写预计费用之和，缺失项单独提示。V3 分开统计实际费用和按当前成员人数算的人均。

时间校验分三级：结束早于开始返回 400；重叠和越界只进体检提示，不拦写入。重叠用扫描线找「与当前最晚结束项相交」的对，不把互相重叠的 n 项展开成 n² 条提示。

为什么重叠不拦写入：编辑过程中会短暂出现中间状态，比如正在调换上下午顺序。服务端直接拒绝会挡掉正常操作。

## 4. 邀请与并发

创建者按用户名邀请，服务端校验目标账号，创建待处理邀请。受邀者接受后加入成员集合，拒绝后保留处理结果。

行程版本从创建时开始递增。更新请求必须提交读取时的版本，服务端在同一写入锁内比较、保存、递增，不一致返回 409。客户端重新读取后由用户决定怎么合并。

留言、修改记录、候选、选票都是旁路数据，都不进行程聚合，因此不推进版本号。操作记录由服务端在写操作成功后产生，`actor` 取会话身份，客户端提交不了。

## 5. 本地文件与恢复

用 UTF-8 JSON 文本文件保存账号、邀请、行程、候选、选票、留言和修改记录。启动时读取并校验结构。

写入串行化：先写临时文件，刷新后替换正式文件。失败保留原文件并报错。损坏文件不自动覆盖，提示从备份恢复。运行态文件缺失时由 Store 自动创建，不需要预置空数组种子。

为什么不用数据库：课程设计阶段要保证「克隆下来就能跑」，不引入额外的服务依赖。做完整票务交易前要重新评估，订单、超时查单、回调去重靠 JSON 文件撑不住。

## 6. 留言、记录、投票与导出

留言和修改记录各自落盘（`comments.json`、`changelog.json`），都不进行程聚合。

候选与选票同样独立落盘（`candidates.json`、`votes.json`）。投票不自动改变行程，只做讨论依据。归档标记放在行程聚合根上，「归档即全站只读」的判断点和版本校验因此在一处。

导出由客户端选本地路径，服务端生成授权范围内的文本摘要。

## 7. 验证

JUnit 覆盖预算、时间、权限、邀请、版本冲突、对话工具分发和投票编排。用临时目录测保存、重启读取和损坏文件处理。模拟模型和地图接口的超时、错误与非法结果。

端到端验收在 `tools/acceptance.py`，68 个断言，覆盖注册、鉴权、Agent 降级、灵感排序、票价字段。

现状：79 个测试类、634 个 `@Test`。真实密钥配好后，端到端成功调用链路还没留下记录，只验证过降级路径。

## 8. 购票辅助与后续交易

票务只做辅助：查 `ticket_channels.json` 白名单，命中就给官方入口、票价规则和查询时间，未命中就说「无经核验入口」，不生成猜测链接。库存状态一律标「余票未核验」。

完整交易未实现。将来要做需要在拿到正式接口与授权后另建 `TicketingGateway`、订单服务和持久化：复核产品、场次、价格和库存，展示订单预览，用户确认后下单并跳转支付，核验出票后更新行程与预算。下单幂等、超时查单、回调验签与去重、状态恢复和退款核验由 Java 服务执行。身份证等资料通过受控表单收集，不进模型上下文，也不进普通日志。

## 9. 对话与解析能力

**意图解析**（`POST /api/intent/parse`）。把一句话拆成五个槽位，本身不回答任何问题。原来靠前端正则抠天数、人数、预算，用户说「下周六带爸妈去武当山玩四天，预算六千」时只能认出「四天」。

**地名归属**（`POST /api/places/resolve`）。先用知识库精确反查，查不到交给模型判断归属，再查不到就转实时检索。避免「黄梅」这类县级地名被判成不认识。

**上下文**。同一会话保留最近几轮，模型能看到上一轮说过什么。会话按 `sessionId` 隔离。

**边界**。对话只出建议，不写文件。写操作一律走行程接口，并且要用户确认。
