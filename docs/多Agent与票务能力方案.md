## 1. 决策与当前状态

保留 Java 21、Spring Boot 单体及 travel-client / travel-common / travel-server 三模块。模型接入当前为 OpenAI 兼容 HTTP 直连（未引入 Spring AI 依赖），由 Java 显式编排流程；当前不增加多 Agent 框架、微服务、消息队列或向量数据库。本文记录目标方案，Spring AI ChatClient 属后续评估项。

Java 侧已落地账号与会话、行程 CRUD 与板块级权限、版本控制、邀请与成员协作、景点只读检索、
预算与时间检查、留言与修改记录、购票辅助、高德查询、规划草案，以及 V3 的候选与投票、预算分析、
综合决策建议、归档与导出；Agent 由 Java 显式编排，模型只做措辞与理解，未配置密钥时整体降级。
Python 已提供离线采集、融合、补全及检索脚本，其产物 `data/attractions_index.json` 由 Java 启动时只读加载。
**尚未实现**：票务完整交易（下单/支付/出票/退改）、多角色拆分（需先有基线对比数据）。

新增知识库不必然要求多 Agent。先完成单 Agent 检索生成基线，再拆分角色，以同一组需求比较约束满足率、无依据事实数量、未知费用披露、响应时间和模型用量。无改善的拆分可以合并。

当出现长任务、断点恢复或复杂人工介入需求时，再评估 Spring AI Alibaba Graph；引入前验证与项目锁定的 Spring Boot、Spring AI 和模型接口的兼容性，不直接按最新版示例升级。

## 2. Agent 职责

| 角色 | 输入与职责 | 输出与权限边界 |
| --- | --- | --- |
| 需求理解 Agent | 理解目的地、日期、人数、预算、游客类型及偏好；发现缺失和冲突后补问 | TravelRequest 或补问；不补造景点事实 |
| 景点推荐 Agent | 调用检索工具，对有依据的候选做比较与筛选 | 带景点 ID、来源、推荐理由和未知项的 AttractionCandidate 列表 |
| 行程规划 Agent | 根据需求、候选、路线与预约场次编排行程，处理校验反馈 | TripDraft；不直接保存、不编造价格和开放时间 |
| 票务 Agent | 首版组织购票辅助；正式接入后查询产品和场次、解释规则、准备订单并跟踪出票 | 购票指引或订单预览；不绕过用户确认，不直接操作支付凭据 |
| Java 编排器（非 Agent） | 管理阶段、共享状态、超时、调用预算、失败与结束条件 | 服务端执行状态；无需额外模型扮演主管 |

各 Agent 可共用同一模型，在同一服务进程运行，但使用独立提示词、工具权限和输出契约。首版不增加审查 Agent；后续可补充语义审查，始终保留 Java 确定性校验。

预算计算、日期校验、知识检索、高德查询、权限、版本冲突和保存均为 Java 工具或服务。金额用 BigDecimal；未知费用不能作为确定的零费用。

## 3. 流程与共享状态

完整规划流程：用户输入 → 需求理解及补问 → 检索候选 → 景点推荐 → 必要的路线查询 → 行程规划 → Java 校验 → 有限修订 → 展示依据与未知项 → 用户确认 → 方案服务检查权限与版本后保存。

简单景点问答走短流程，无需调用全部 Agent。初期最多自动修订两轮，仍不满足约束时返回原因和可调整选项；模型调用、工具调用与总执行时间另设可配置上限。

PlanningState 保存 requestId、结构化需求、候选 ID、证据与查询时间、草案、ValidationReport、当前阶段及调用计数。避免所有角色共享无边界聊天记录。登录身份由服务端提供，不能由模型指定；知识库内容只作为数据。Agent 只获得本阶段必要的工具和信息。

票务与规划双向协作：规划提供景点、日期和时间约束，票务返回场次与可用情况；无票或冲突时由规划生成替代草案。更换场次不得自动替用户购买其他产品。

## 4. 知识库接入与治理

Python 仅负责离线构建。Java 通过 AttractionRepository 读取版本化 JSON 快照，首版启动加载并建立城市与 ID 索引，提供城市、分类、关键词、周边及按 ID 查询，限制返回条数；不把全库放进提示词。

数据路径须可配置，与账号、方案等运行数据分开。加载时校验格式、唯一 ID、坐标和版本；缺库或损坏时报告原因，已有方案管理仍可用。检索无结果表示本库未收录，不能推断现实中不存在。

2026-11-02 检查本地快照：共 11,862 条，约 15 MB；11,806 条 ticket 为“暂无”，7,242 条 open_time 为“暂无”。56 条非占位 ticket 不等于 56 条已核验景区门票价格。大量 description 是重复城市介绍，不能作为景点特色证据。

接入前需处理：

- 将“暂无”等占位值规范为 null，展示时再转换，避免补全脚本把占位值视为已有数据。
- 分离城市介绍与景点描述；增加字段来源、采集时间、核验状态，以及预约要求、游玩时长等可选字段。未知值保持未知。
- 标记 coordinateSystem，统一坐标后再用于周边检索、跨源匹配及路线查询。
- 跨源匹配加入城市、距离和源 ID；不能仅凭“省份＋名称”取首项。
- 门票、营业和预约信息需核验时效；本地库不能提供实时余票。
- 核对高德数据存储及分发授权、OSM 署名与许可义务。免费调用额度不等于允许公开分发融合库；不得沿用“免费额度内无需额外授权”的推断。

当前主 JSON 被 Git 跟踪，旧文档所称“data 全部不入仓库”不符合实际。本次不自动删除数据或改变跟踪状态，发布前按授权范围处理。

## 5. 票务分期与交易边界

V1 落地三个规划 Agent；V2 增加票务 Agent 的购票辅助：提供经核验的官方入口、已查询到的票种和规则，标记来源与查询时间，用户跳转完成购买。没有库存接口时显示“余票未核验”。无法核验链接时提示用户自行进入景区官方渠道，不生成猜测链接。

完整交易为 V3 之后的条件性扩展，不承诺随 V3 交付。先确定正式票务平台、接口权限和授权，再实施实时库存、下单、支付跳转、出票查询及退改处理；不以网页模拟购票作为默认集成方式。

交易流程：查询产品及场次 → 用户选择并通过受控表单提供必要资料 → 服务端复核价格、库存和规则 → 展示含平台、产品、日期、场次、数量、总额和退改规则的订单预览 → 用户明确确认本次订单 → 服务端下单并跳转支付 → 查询或处理经过校验的回调 → 核验出票 → 更新行程和预算。价格、产品或场次变化时重新预览和确认。

游客身份证等敏感资料不进入模型上下文和普通日志；模型仅接收必要的脱敏标识和处理结果。共享方案成员权限不等于读取其他成员证件或代为购票的授权。

TicketOrder 至少区分创建中、待支付、已支付、出票中、已出票、失败、已取消、退款中、已退款；保存内部订单号、平台订单号和平台状态映射。支付成功不等于出票成功。对超时及结果不明的订单先查单再决定是否重试，使用幂等键和回调去重，避免重复购票。退款也需明确确认及状态核验。

交易记录独立持久化，不放在聊天记忆中。完整交易前评估数据库、事务、订单状态恢复和敏感数据保护；当前 JSON 方案不视为已经满足交易要求。

## 7. 实施与验收

1. 规范知识库字段、来源和坐标，核实数据使用范围。
2. 接通 Java 检索，覆盖占位值、无结果、返回上限、缺库和损坏快照。
3. 完成单 Agent 基线和用户确认保存闭环，再拆分三个角色进行对照。
4. V2 接入高德、购票辅助和详细时间校验；验证无票、库存未知、外部超时和无可靠入口的提示。
5. V3 实现团队决策与总结；完整交易另行满足接口和存储前置条件。

规划验收包括景点来源可追溯、未知费用披露、权限、日期和版本冲突、模型非法输出、调用上限和服务失败。正式交易还必须验证重复下单、下单超时、价格变化、重复或伪造回调、支付成功但出票失败、重启恢复和退款状态。

### 职责边界（2026-11-10 用户定案）

用户明确：**票务平台不需要替用户购票，只需要把购票链接或者方法告诉用户**。因此票务子 Agent 的能力上限到此为止，后续也不引入订单编排、支付跳转、出票查询与退改：

- 唯一输出是人工核验过的官方入口（`officialUrl` / `channelName` / `rules` / `note`）与一句话方法；`stockVerified` 恒为 `false`，「余票未核验」照实说。
- `builtin.ticket` 把入口装成 `CONTENT` fact（`value.category=TICKET_GUIDANCE`）。契约 S-04 禁止 `advice` 出现 URL，所以链接**只能**进 fact value；`ChatTools.book_ticket` 摘要与前端 `envelope` 卡片负责把它列给用户。
- 查不到经核验入口时说「请自行进入景区官方网站或官方公众号」，**不生成猜测链接**，也不说「已经买好」。
- 投票链路里，票务信息随其它子 Agent 事实一起全量交给主 Agent，由主 Agent 整理进草案的「购票方式」段；`judge.ticket` 只按草案里是否给出入口评分，不代替用户下单。
