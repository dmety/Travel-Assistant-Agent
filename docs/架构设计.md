## 二、各层涉及的内容

### 第一层：客户端表现层

客户端有三种形态，都在用户自己的电脑上运行。

**浏览器页面**（`travel-server/src/main/resources/static/`）：

| 页面 | 大小 | 职责 |
|---|---|---|
| `index.html` | 16 KB | 登录与注册。`/`、`/login`、`/app` 由 `PageController` 转发到这里 |
| `chat.html` | 113 KB | 对话页。模型自己决定查什么工具，查完再回答 |
| `api-console.html` | 95 KB | 接口测试台，带独立登录卡 |
| `ticket-assistant.html` | 34 KB | 景区购票助手，只展示经核验的官方入口 |

**Java 控制台客户端**（`travel-client`）：`TravelClient` 做健康检查，`AttractionConsole` 查景点。功能弱于网页，保留用于命令行环境。

**共同约束**：通过 HTTP 调用共享服务，不直接改服务端数据文件。

### 第二层：服务接口层

20 个 Controller，88 个映射。按职责分四组。

**账号与页面**：`AccountController`（注册、当前用户）、`PageController`（页面转发）、`HealthController`。

**行程业务**：`ItineraryController`（CRUD、五大板块、成员）、`InvitationController`（邀请的五种状态流转）、`CollaborationController`（留言与修改记录）、`CandidateController`（候选与投票）、`AgentVoteController`（三评委两轮投票）。

**信息查询**：`AttractionController`（按城市/名称/ID 查知识库）、`TicketController`（官方入口与票价规则）、`TicketAssistantController`（购票助手）、`LocationController`（地点、天气、路线）。

**Agent 与解析**：`AgentController`（规划草案与决策建议）、`AgentInvokeController`（L1 编排入口）、`AgentCapabilityController`（能力协商）、`ChatController`（对话）、`IntentController`（意图解析）、`PlaceController`（地名识别）、`AdmissionController` 与 `DefaultAdmissionController`（准入判定）。

公共处理：解析请求、校验格式、识别登录身份，把业务异常映射成 HTTP 状态码（`ApiExceptionHandler`）。

### 第三层：业务服务层

16 个包。核心是三条：行程业务、查询、Agent。

**行程与协作**：`itinerary`（7 个类）、`invitation`（5）、`collaboration`（4）、`account`（4）。

**计算与分析**：`budget`（预算汇总与体检）、`decision`（综合决策建议）、`export`（文本导出）。

**查询与票务**：`attraction`（3）、`ticket`（4）、`location`（2）、`map`（`MapTools`，高德主源加百度第二源）。

**Agent**：`agent`（19 个类，含 `orchestration`、`vote`、`spi`、`food` 四个子包）、`chat`（3）、`intent`（6）、`place`（4）。

预算、日期和权限一律由 Java 校验。模型只出建议，用户确认后才由行程服务保存。

### 第四层：领域模型层

11 个包，纯模型与规则，不依赖 HTTP、Spring 和文件格式。

| 包 | 内容 |
|---|---|
| `itinerary`（10 类） | `Itinerary` 聚合根、`Plan`、`DailySchedule`、`DailyActivity`、`Transport`、`Lodging`、`Expense`、`Member`、`Section` |
| `budget`（9） | `BudgetCalculator`、汇总与体检模型 |
| `decision`（7） | 决策建议与风险项 |
| `location`（5） | `Place`、`WeatherResult`、`RouteResult`、`RouteMode` |
| `ticket`（4） | `TicketChannel`、`TicketType`、`TicketAdvice` |
| `invitation`（3） | `Invitation` 与状态机 |
| `attraction`（2） | 景点只读模型、占位值规范 |
| `collaboration`（2） | `Comment`、`ChangeEntry` |
| `food`（1） | 餐饮推荐模型 |
| `trip`（1） | 早期分包遗留，功能已并入 `itinerary` |
| `repository`（1） | 仓储职责说明，实际由各 Store 实现 |

### 第五层：基础设施与外部服务层

7 个包。

- `persistence`（9 类）：账号、行程、邀请、协作、候选、投票、景点等 JSON 仓库。写入用临时文件替换，保证原子性。
- `security`（2）：`SecurityConfiguration`、`JsonUserDetailsService`。密码用 BCrypt。
- `ai`（2）：`DeepSeekClient`，走 OpenAI 兼容 HTTP，不走 Spring AI。
- `amap`（2）：地点、天气、路线。未配密钥时返回 503 并说明原因。
- `baidu`（2）：第二数据源，补齐高德查不到的 POI。返回 BD-09 坐标，由 `geo` 转 GCJ-02。
- `geo`（1）：坐标系转换。
- `ticketing`（1）：`TicketChannelStore`，只读官方入口白名单。

密钥全部通过环境变量注入，不写进仓库。

## 三、典型调用路径

**对话回答**：`chat.html` 提交一句话 → `ChatController` → `ChatAgent` 带上 8 个工具的清单请求模型 → 模型决定调哪个工具 → Java 执行工具并回填结果 → 模型组织语言 → 页面按步骤展示。

**一句话解析**：`POST /api/intent/parse` → `IntentParser` 把「下周六带爸妈去武当山玩四天，预算六千」拆成目的地、天数、人数、预算、偏好五个槽位，本身不回答问题。

**地名归属**：`POST /api/places/resolve` → 模型判断「黄梅」属于黄冈 → 查不到就转实时检索，不要求用户重说。

**生成行程草案**：客户端提交需求 → `AgentController` → 编排层 → 检索知识库 + 查天气 → 返回草案与补问项 → 用户确认 → 调用行程接口保存。草案不落库，模型建议与落库数据之间隔着一次人工确认。

**三评委投票**：`POST /api/agent/vote` → 三个评委 Agent 各自出一版方案 → 两轮投票 → 主 Agent 汇总。只出比较结果，不保存。

**共同编辑**：读取行程及版本 → 提交修改 → 服务端在同一写入锁内比较版本、保存、递增 → 版本不一致返回 409，客户端重新读取。

**购票辅助**：`/api/tickets` → 查 `ticket_channels.json` 白名单 → 命中就给官方入口与方法，未命中就说「无经核验入口」，不生成猜测链接。

## 四、部署与限制

- 单体 Spring Boot 服务，多人连同一个实例。文本文件存在服务端本地，重启后读取。
- 写入由单个进程串行管理。不支持多个实例同时写同一份文件。
- 服务停止或网络中断时无法共享编辑。文件损坏或磁盘故障仍会丢数据，需要定期备份。
- 跨设备部署应上 HTTPS，并保护数据目录。外部接口的权限、配额和费用要在接入前核实。

## 六、认证与 Agent 执行约定

**会话认证**：Spring Security 管登录态，`JSESSIONID` 带 HttpOnly 和 SameSite=Strict。会话存内存，重启后重新登录，历史行程不受影响。未认证请求返回 401，不跳登录页。

**匿名可达的路径**：`/api/health`、`/api/login`、`/api/account/register`、`/api/attractions/**`、`/api/tickets/**`，以及三个只返回布尔与能力描述的状态接口（`/api/location/status`、`/api/agent/status`、`/api/agent/capabilities`）。四个页面本身公开，数据仍由 `/api/**` 拦截。

**必须登录的**：`/api/agent/invoke`、`/api/agent/tickets/advice` 等会消耗模型与地图配额的入口。

**权限实时检查**：服务端按当前成员关系授权。成员被移除后立即失去访问权。工具沿用同一套检查，模型不能指定操作身份。

**受控执行**：模型不读写文件。工具调用有次数与超时限制，参数和输出都要校验。正式修改必须经用户确认，再走权限、时间、版本检查。

### V3 的三条结构性决定

| 决定 | 理由 |
|---|---|
| 候选与选票独立落盘，不进行程聚合 | 投票是讨论，不是改方案。进了聚合，讨论就会引发 409 |
| 归档标记放在行程聚合根上 | 「归档即全站只读」的判断点和版本校验在同一处，不会漏掉写入口 |
| 决策建议的风险由 Java 规则算出 | 预算差额、时间冲突、交通衔接都能用数字说清，交给模型就有编造空间 |

## 八、项目结构的设计理由与取舍

### 1. 为什么分三个 Maven 模块

跨电脑协作要求客户端通过同一后端访问共享数据，所以把交互和业务处理分开。共享契约单独维护，避免两端字段对不上。

| 模块 | 理由 | 边界 |
|---|---|---|
| travel-client | 各人在自己电脑上交互，通过网络访问同一服务 | 不读写服务端文件，不依赖后端实现 |
| travel-server | 集中管权限、行程、Agent、版本与文件写入 | 保持单体，不拆微服务 |
| travel-common | 复用请求响应结构，减少重复定义 | 不放业务对象、存储实现或杂项 |

三个模块在同一个父工程内构建，独立模块是代码边界，不是三个服务。

### 2. 为什么服务端按职责分层

| 目录 | 负责什么 | 分开的价值 |
|---|---|---|
| interfaces/rest | 收请求、解析、返回 | HTTP 变化不影响预算与时间规则 |
| application | 组织权限、校验、Agent、保存 | 完整业务流程集中在一处 |
| domain | 行程、安排、费用及其规则 | 核心规则能脱离网络和文件测试 |
| infrastructure | JSON、模型、地图、安全的适配 | 隔离技术细节，便于替换和模拟失败 |

以成员改行程为例：接口收请求，应用服务查身份和成员权限、调领域校验、经仓储保存。版本比较与保存必须在同一临界区。领域对象不直接碰文件和网络。

### 3. 为什么 Agent 单独编排

Agent 管需求理解、补问、工具调用和建议生成，行程服务管正式修改。手动编辑和 Agent 建议确认后走同一套权限、预算、时间、版本检查，避免两套规则打架。模型不写文件，工具也不能绕过当前用户的授权范围。

11-09 之后又加了一层：编排层只认 `AgentProvider` 接口，具体 Provider 靠配置注册。这样加一个 Agent 不用改编排代码，失败时也能切兜底。

### 4. 为什么不用 Spring AI

11-02 的原方案是 Spring AI 加 Java 显式编排三个角色。实际接入时发现两个问题：缺密钥时 `ChatClient` 会让上下文启动失败；工具调用的可控性不如自己拼 HTTP。改成 OpenAI 兼容 HTTP 直连后，没配密钥也能启动，工具参数由 Java 逐个校验。
