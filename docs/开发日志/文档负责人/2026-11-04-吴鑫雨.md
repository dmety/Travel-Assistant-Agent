### 3. 逐篇比对文档与代码

文档的价值取决于它和代码是否同源。本次以「文档声明 → 代码事实」逐条核对，重点三处：公开入口清单、接口路径、目录结构。

公开入口的核对对象是 `SecurityConfiguration` 的 `permitAll()` 列表，实际放行 9 项：

```text
/api/health, /api/login, /api/account/register, /, /login, /login.html,
/register.html, /app, /app.html
```

而接口文档第 1.3 节只列了 7 项，`/app` 与 `/app.html` 未收录——这两个入口是 PR #5 里随 `app.html` 测试前端一起加的（`PageController` 的 `@GetMapping("/app")`）。反过来，`/register.html` 在文档与安全配置里都有，但 `travel-server/src/main/resources/static/` 下只有 `app.html` 和 `login.html`，这一页并不存在。

接口路径方面，`ItineraryController` 实际提供 21 个映射（创建/列表/详情/删除 + 五板块各 GET/PUT + 成员增删改），与接口文档第 3 章逐条对得上，这部分无需修改。

## 三、文档缺陷清单（本轮新发现）

严重度按影响面定：P1 = 会导致读者按错误信息操作或链接直接打不开；P2 = 内容与事实不符但可自行推断；P3 = 体例或表述问题。

### F-1（P1）《测试说明》从未入库，4 处引用全悬空

- **位置**：`docs/开发日志/测试负责人/2026-11-03-李橙子.md` 第 27、89、166、176 行
- **实测**：全仓库提及「测试说明」共 4 处，其中第 89 行是 Markdown 链接 `../../测试说明.md`，脚本判定断链；`docs/` 下无此文件。
- **影响**：测试负责人按「更新 `测试说明.md` 里的环境前提」布置了后续任务，但该文件不存在，任务无法执行；新成员也无从得知 `mvn test` 的正确跑法。
- **建议**：补写 `docs/测试说明.md`，至少含 Maven 环境前提、测试分层（接口/并发/缺陷回归）、临时数据目录隔离约定。

### F-2（P1）README 状态描述已过期，与主干事实相反

- **位置**：`README.md` 第 5 行「当前交付为可连接的工程骨架……业务功能尚未实现。」
- **实测**：`main` 已合并 PR #5 与 PR #6，账号体系（注册/登录/会话/BCrypt 落盘）与行程 CRUD（五板块、细粒度权限、乐观锁）均已落地并通过 66 条用例；开发负责人与测试负责人日志都以「已落地功能」为前提写作。
- **影响**：README 是仓库门面，也是评审第一个打开的文件。按此描述会低估完成度，与测试负责人「不建议判验收通过」的结论叠加后，容易得出「几乎没做」的错误判断。
- **建议**：改为「已实现：账号与会话、行程 CRUD、板块级权限、JSON 持久化；未实现：Agent 编排、高德接入、预算汇总、V2/V3」，并附一句指向最新开发日志。

### F-3（P1）README 文档目录首条断链

- **位置**：`README.md` 「文档目录」第 1 条 → `docs/团队管理/使用说明-简易版.md`
- **实测**：`docs/团队管理/` 目录不存在，脚本判定断链。
- **影响**：读者点第一个链接就 404。
- **建议**：若该说明存放在飞书（README 同段提到「两张表管理任务进度」，应为外部协作文档），改为外链并标注「外部文档」；若已废弃，直接删除该条。

### F-4（P1）接口文档公开入口清单与安全配置不一致

- **位置**：`docs/服务端REST接口文档.md` 第 1.3 节
- **实测**：
  - 漏收 `/app`、`/app.html`——`PageController` 有 `@GetMapping("/app")`，`static/` 下有 `app.html`，安全配置也已放行。
  - 多收 `/register.html`——安全配置放行了该路径，但 `static/` 下无此文件，注册实际走 `login.html` 内嵌表单。
- **影响**：前端照文档接 `/app` 会以为需要登录；照文档找 `/register.html` 会拿到 404。
- **建议**：以 `SecurityConfiguration` 为准重写 1.3 节；`/register.html` 需二选一——补页面，或从放行列表与文档中同时删除。

### F-5（P2）接口文档的分支口径已失效

- **位置**：`docs/服务端REST接口文档.md` 第 3 行「适用分支：`zipei`」
- **实测**：行程与账号功能已在 `8214902` 合入 `main`。
- **影响**：读者会以为这些接口只在个人分支可用，不敢按文档对接。
- **建议**：改为「适用版本：`main`（自 `8214902` 起）」。

### F-6（P2）架构设计的 docs 目录树与实际不符

- **位置**：`docs/架构设计.md` 第 176–196 行目录树
- **实测**：树中列 `docs/README.md`（不存在），漏列《服务端REST接口文档》《知识库使用文档》《多Agent与票务能力方案》《跨源同名风险审核清单》4 篇。
- **影响**：架构文档是新人理解项目的入口，目录树缺项会让人以为这些文档不属于正式体系。
- **建议**：按实际 9 篇重排目录树，并注明日志归档方式。

### F-7（P2）知识库文档的示例代码被当成接口约定

- **位置**：`docs/知识库使用文档.md` 第 204–215 行「方式 B」`@RequestMapping("/api/kb")`
- **实测**：代码库中无任何 `/api/kb` 实现（`grep` 结果为空），该段是接入示意。但测试负责人日志第 174 行已将其当作「路径约定」，要求「落地后按 `/api/kb/city/{name}`、`/api/kb/search?q=` 补接口测试」。
- **影响**：一份「示例」被下游当成「规格」，接口一旦按此实现就失去调整空间。
- **建议**：在代码块前加一行「以下为示意，当前未实现；正式路径待接口文档定稿后同步」。

### F-8（P2）数据治理文档引用本机绝对路径，他人无法复核

- **位置**：`docs/cross_source_review.md` 第 3、113 行
- **实测**：引用 `F:/wb_tmp/cross_source_audit.json` 与 `F:/wb_tmp/merge_log.json`，均为生成者本机路径；仓库内 `data/` 已有知识库主体。
- **影响**：审计过程不可复核，等于结论无法被验证。
- **建议**：把审计与合并日志的产物一并入库（如 `data/audit/`），文档改指相对路径；确属临时产物的，注明「外部中间产物，未入库」。

### F-9（P3）同一实体两个称呼，版本口径四份并行

- **实测**：需求文档称「方案」，接口文档与代码称「行程（Itinerary）」；版本说明分散在需求文档第 4 章、各版本功能模块、三个递进版本、多Agent与票务能力方案四处，需求文档仅一句「以专项方案为准」。
- **影响**：新人易把「方案」与「行程」当成两个对象；四份版本说明无优先级标注，改需求时不知道改哪份。
- **建议**：统一为「行程（Itinerary）」，首次出现处标注旧称；在 README 文档目录为四份版本说明加一行层级说明（专项方案 > 需求文档 > 各版本功能模块）。
