# data 目录优化（2026-11-08）

## 结论

分两轮清理。第一轮删掉 `data/kb_modules/` 的 8 个模块文件，共 10,584,437 字节（约 10.1 MiB）；第二轮按用户追问「example 呢」再删掉 7 个 `*.example.json` 空数组种子，共 42 字节。分片、主库、索引字节均未变，门禁与 Java 运行链不断。

删除后 `data/` 实测 42 个文件、17,428,194 字节（约 16.6 MiB）：`attractions/` 下 31 个，顶层 11 个（4 个入库的配置与产物，7 个未入库的运行态 JSON）。文件数会随服务启动创建运行态文件浮动，不是固定值。

先做只读盘点：逐个查体积、是否被代码引用、是否入库，再决定去留。

| 主库产物 | `china_attractions.json` | 6.30 MiB | `build_attraction_index.py`、30 余个 `tools/kb/` 脚本、`quality_report`、治理门禁 | 保留 |

| 字段派生视图 | `kb_modules/` 下 8 个文件 | 10.1 MiB | 仅 `gate.sh` 交叉校验与 `--sync` 生成 | **删除（第一轮）** |

## 删除依据

`kb_modules/` 是上午按字段分层留下的编辑源，下午按省分片后已降级为纯派生视图：不手工编辑、不参与运行、内容与分片和主库完全重复，`--sync` 每次都会重建。它占 `data/` 近四成体积，却没有任何独立信息，是唯一能无损删除的大块。

7 个 `*.example.json` 各只有一个空数组 `[]`。全仓检索没有任何 Java、Python 或 shell 代码读取 `.example.json`；`AccountStore#init()` 在目标文件不存在时直接 `write(accounts)` 创建空文件，其余 Store 同理，`docs/服务端REST接口文档.md` §7 也写明「新克隆无需手工拷贝即可启动」。种子只用来说明初始形态，不是运行必需品。上一轮把它判为保留，理由是「删了没收益还破坏文档口径」，这个理由不成立：42 字节的摆设加上六处过时口径，本身就是维护负担。

两次删除都用 `git rm`，文件均已入库，需要时 `git checkout` 可完整恢复。`tools/kb_modules.py` 保留为可选的本地视图生成工具，运行 `--split` 可随时重建视图；生成的目录受 `/data/*` 黑名单约束，不会重新入库。

## 未决

运行态 7 个 json 未删。它们是本地账号、行程、评论与变更记录，删除会清空本地数据；虽然只有几 KiB 且已被黑名单排除、不占仓库，但属于有状态数据，需要显式确认才动。

主库与索引仍在仓库，为的是新克隆开箱即用。若要连它们一起移出版本控制，需把索引构建接进首次启动流程。主库 6.30 MiB 仍是最大的单文件，但被 30 余个离线脚本硬编码读取，本次不动。
