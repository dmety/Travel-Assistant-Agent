## 二、D-6（P0）乐观锁在并发下失效

### 现象

同一行程、同一版本号并发提交，多个请求同时返回 200，但只有最后一次写入生效，其余静默丢失。

实测（2026-11-05，12 路并发携带 `version=1`）：

| 场景 | 每轮 200 成功数 | 丢弃的更新 |
| --- | --- | --- |
| 冷 JVM 首轮 | 12 | 11 |
| 预热后 12 并发 × 10 轮 | `1,1,1,1,2,1,1,1,1,1` | 1 |
| 预热后 30 并发 × 5 轮 | `1,2,1,1,1` | 1 |

**注意：这是间歇性的，单次跑出「1 个 200」不能说明已修复。** 判定请用 `OptimisticLockAtomicityTest`，它用栅栏把竞态变成必然，跑一次即可。

### 根因

`ItineraryService` 每个写方法都是同一个模式，以 `updatePlan` 为例（`application/itinerary/ItineraryService.java:62-69`）：

```java
public Itinerary updatePlan(String id, String user, Plan plan, long version) {
    Itinerary it = requireExists(id);        // ① 读快照
    requireEdit(it, user, Section.PLAN);
    checkVersion(it, version);               // ② 比对版本（锁外）
    Itinerary updated = it.withPlan(plan);
    store.save(updated);                     // ③ 加锁写入
    return updated;
}
```

`ItineraryStore.save` 虽然有 `synchronized`（`ItineraryStore.java:62`），但**版本比对发生在进锁之前**。两个线程可以在同一时刻都通过 ②，然后排队通过 ③，后写覆盖前写。

同样模式出现在 8 个方法：`updatePlan`(62)、`updateDaily`(75)、`updateTransports`(93)、`updateLodgings`(109)、`updateExpenses`(124)、`addMember`(141)、`updateMember`(154)、`removeMember`(167)。

顺带一个隐患：`requireEdit` 也是基于 ①的旧快照判断权限的，锁内应重新取快照。

### 修复方案 A（推荐，改动最小）

在 Service 里给「读 → 校验 → 写」加同一把锁。`ItineraryService` 是单例，一把实例锁即可覆盖全部写方法。

```java
/** 写操作串行化：保证「读版本 → 比对 → 落盘」原子，见缺陷 D-6。 */
private final Object writeLock = new Object();

public Itinerary updatePlan(String id, String user, Plan plan, long version) {
    synchronized (writeLock) {
        Itinerary it = requireExists(id);
        requireEdit(it, user, Section.PLAN);
        checkVersion(it, version);
        Itinerary updated = it.withPlan(plan);
        store.save(updated);
        return updated;
    }
}
```

其余 7 个写方法照同样方式包一层。`create` / `get` / `listForUser` 不需要。

代价：同一 JVM 内所有行程的写操作串行。本项目是课程作业规模，完全可接受；真要并发再上方案 B。

### 修复方案 B（更彻底，但不急）

把「比对 + 写入」下沉到 `ItineraryStore`：

```java
public synchronized Itinerary update(String id, long expectedVersion,
    UnaryOperator<Itinerary> mutator) {
  Itinerary current = items.stream().filter(i -> i.id().equals(id)).findFirst()
      .orElseThrow(() -> new ItineraryNotFoundException(id));
  if (current.version() != expectedVersion) {
    throw new VersionConflictException(current.version());
  }
  Itinerary updated = mutator.apply(current);
  List<Itinerary> next = new ArrayList<>(items);
  next.removeIf(i -> i.id().equals(id));
  next.add(updated);
  items = next;
  write();
  return updated;
}
```

注意层次问题：`ItineraryStore` 在 `infrastructure.persistence`，而 `VersionConflictException` / `ItineraryNotFoundException` 在 `application.itinerary`。这样做会形成 infrastructure → application 的反向依赖。若走方案 B，先把这两个异常下沉到 `domain.itinerary` 再改，同时修正 `OptimisticLockAtomicityTest` 的 import。

### 验收

```bash
# 删掉 OptimisticLockAtomicityTest 类上的 @Disabled，只跑这一条
mvn -B test -Dtest=OptimisticLockAtomicityTest -Dsurefire.failIfNoSpecifiedTests=false
```

- 修好：`Tests run: 1, Failures: 0`，一次通过，不需要重复跑。
- 未修好：`expected: 1 but was: 2`。

> `OptimisticLockStressTest` 已降级为参考用例，它变绿**不构成**修复证据。

## 三、D-4（P0）费用金额允许为负数

### 现象

`PUT /api/itineraries/{id}/expenses?version=1`，`amount = -999.99` 返回 200 并落盘。

### 根因

`ItineraryService.updateExpenses`（:124-133）只做 `fillIds` 补 id，没有任何值校验。

需求依据：[各版本功能模块](./旅行助手-各版本功能模块.md) V1 第 5 条「检查费用是否为非负数；未填写费用标记为待填写」。

### 修复

1）新增异常（`application/itinerary/InvalidSectionException.java`）：

```java
public class InvalidSectionException extends RuntimeException {
  public InvalidSectionException(String message) {
    super(message);
  }
}
```

2）`ApiExceptionHandler` 补一条映射，转 400：

```java
@ExceptionHandler(InvalidSectionException.class)
public ResponseEntity<Map<String, Object>> invalidSection(InvalidSectionException e) {
  return ResponseEntity.badRequest().body(Map.of("error", e.getMessage()));
}
```

3）`updateExpenses` 里加校验（放在锁内）：

```java
private void validateExpenses(List<Expense> expenses) {
  if (expenses == null) {
    return;
  }
  for (Expense e : expenses) {
    if (e.amount() == null) {
      throw new InvalidSectionException("费用金额不能为空");
    }
    if (e.amount().signum() < 0) {
      throw new InvalidSectionException("费用金额不能为负数：" + e.amount());
    }
  }
}
```

### 验收

删掉 `KnownDefectTest.negativeExpenseAmountIsRejected` 的 `@Disabled`，应返回 400。

## 四、D-1 / D-5（P1）

### D-1 邀请未注册账号也能成功

`addMember` 只往成员列表写 `username`，不校验账号是否存在。

改法：给 `ItineraryService` 注入 `AccountStore`，在 `requireOwner` 之后加：

```java
if (!accountStore.exists(memberUser)) {
  throw new InvalidSectionException("用户不存在：" + memberUser);
}
```

> 注意：`updateMember` 也要判——先确认该成员已在列表里再改（这条同时解决 D-3）。

### D-5 住宿离店早于入住未被拦截

需求依据同上一条文档 V1 第 5 条（时间校验）。

```java
private void validateLodgings(List<Lodging> lodgings) {
  if (lodgings == null) {
    return;
  }
  for (Lodging l : lodgings) {
    if (l.checkIn() != null && l.checkOut() != null && l.checkOut().isBefore(l.checkIn())) {
      throw new InvalidSectionException(
          "离店日期不能早于入住日期：" + l.checkIn() + " → " + l.checkOut());
    }
  }
}
```

## 五、D-2 / D-3（P2）

### D-2 创建行程不校验标题

1）`CreateItineraryRequest` 的 `title` 加约束：

```java
public record CreateItineraryRequest(
    @NotBlank(message = "标题不能为空") String title,
    @Valid Plan plan) {
```

2）`ItineraryController.create` 参数加 `@Valid`：

```java
public ResponseEntity<Itinerary> create(@AuthenticationPrincipal UserDetails user,
    @Valid @RequestBody CreateItineraryRequest req) {
```

3）`ApiExceptionHandler` 补 `MethodArgumentNotValidException` 处理，保持错误体与其它接口一致：

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<Map<String, Object>> invalidBody(MethodArgumentNotValidException e) {
  String message = e.getBindingResult().getFieldErrors().stream()
      .map(FieldError::getDefaultMessage)
      .findFirst().orElse("参数不合法");
  return ResponseEntity.badRequest().body(Map.of("error", message));
}
```

### D-3 修改不存在成员静默成功且版本 +1

`updateMember` 用 `stream().map(...)` 遍历，找不到目标成员时不报错，但 `withMembers` 照样把版本 +1。

改法：遍历前先确认成员存在：

```java
boolean exists = it.members().stream().anyMatch(m -> m.username().equals(memberUser));
if (!exists) {
  throw new InvalidSectionException("成员不存在：" + memberUser);
}
```

`removeMember` 同理（幂等删除可以保留现状，但与 `updateMember` 行为一致更好）。

# 3) 起真实服务冒烟（必须显式指定端口）

# 测完 kill 掉监听 8080 的 java 进程

两个环境坑，别踩：

- **启动必须带 `--server.port=8080`**：环境里存在 `SERVER__PORT` 变量，Spring 宽松绑定会把它当 `server.port`，导致服务起在错误端口。
- **curl 访问 localhost 要加 `--noproxy '*'`**，否则会被代理拦成 502。

全部 `@Disabled` 删干净且全绿，D-1 ~ D-6 即可判关闭。

## 八、不建议的做法

- **不要靠"多跑几轮"来证明 D-6 修好了。** 这个竞态预热后每轮只有 10%~20% 概率暴露，连跑 5 轮全绿仍可能是运气。判定只看 `OptimisticLockAtomicityTest`。
- **不要用 `@DirtiesContext` 或加大 `@Transactional` 来"绕过"并发测试。** 问题在业务代码的 check-then-act，不在测试环境。
- **不要为了避免 409 而放宽版本校验。** 409 是需求明确要求的行为（需求文档 §4），前端应重读后重试。
