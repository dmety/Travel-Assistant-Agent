# 旅行助手：V1—V3 功能与技术方案

## 一、项目作用

面向经常结伴出游的学生，提供一个 Java 控制台旅行助手。用户通过自然语言描述出游需求，Agent 辅助生成旅行方案；用户可以修改、保存方案，记录目的地、交通、住宿、景点与预算。系统自动汇总预算并检查时间逻辑。用户可以邀请其他账号加入同一方案，在不同电脑上共同编辑。

方案数据保存在服务端的本地文本文件中，服务重启后可恢复。客户端必须连接同一个服务才能共享数据；每台电脑各自保存独立文件无法实现跨电脑协作。

## 二、用户如何操作

1. 在自己的电脑打开控制台客户端，连接共同使用的服务，注册或登录。
2. 选择创建旅行方案，用自然语言描述目的地、日期、预算、偏好和同行人数等需求；信息不足时补充必要信息。
3. Agent 结合用户需求生成草案，用户查看后修改、确认并保存。
4. 方案创建者邀请其他已注册账号加入；受邀用户接受邀请后，可在自己的电脑查看和编辑该方案。
5. 系统根据已填写的费用计算总预算，并校验行程时间；用户修正问题后保存。
6. 以后登录可继续查看和编辑历史方案。

以下为拟定的产品流程，具体交互可在实现时根据测试调整。

## 三、功能模块与版本

每个版本都是可运行、可演示的完整产品；后续版本在前一版本基础上增加能力。

| 模块 | V1：基础协作规划 | V2：信息查询与行程完善 | V3：团队决策与总结 |
| --- | --- | --- | --- |
| 用户与协作 | 注册、登录；创建者邀请账号，受邀者接受或拒绝；成员查看和编辑共享方案 | 增加成员留言和修改记录 | 增加候选地点投票 |
| Agent | 自然语言生成行程草案，用户确认后保存 | 按需调用高德景点、天气、路线工具，基于结果调整草案 | 综合预算、投票和天气等信息提出建议与风险提示 |
| 行程管理 | 创建、查看、修改、删除多条方案；支持两种行程类型 | 完善交通、住宿、景点的时间与路线信息 | 归档结束的行程，导出文本摘要 |
| 预算与校验 | 记录费用、计算总预算；校验出发和返回时间 | 细化费用分类，检查各安排的时间范围和冲突 | 对比预算上限和支出，显示人均费用 |
| 存储 | 服务端文本文件持久化，重启恢复；共享编辑避免覆盖 | 保留成员修改记录 | 保存投票和归档信息 |

### V1：基础协作规划

**用户模块**：注册、登录；创建者按账号发出邀请，受邀者在客户端接受或拒绝。创建者可移除成员和删除方案，成员可查看、编辑方案并退出。

**智能规划模块**：用户以自然语言说明出行需求，Agent 提取目的地、时间、偏好等信息并生成草案；缺少必需信息时向用户追问。用户可以修改并确认草案。V1 的草案主要依据用户输入和模型知识，未接入高德实时查询；对可能过时或未经核实的信息给出提示。

**旅行方案模块**：记录目的地、出发和返回时间、成员、交通、住宿、景点及对应费用；区分短途周末游与长途跨省游，支持多条方案的增删改查。两种类型首先用于分类和面向对象建模，不假定所有周末游都必须严格落在周末或所有跨省游都必须超过某个天数。

**预算与校验模块**：将各项非负预计费用求和；检查返回时间不早于出发时间，提示缺失字段或无效输入。

**数据与冲突模块**：服务端统一读写本地文本文件。每份方案带版本号，客户端提交时携带读取时的版本号；若他人已保存新版本，拒绝覆盖并提示重新读取、合并后再提交。

**验收**：两名用户在不同电脑登录；第一人通过自然语言生成并保存行程，邀请第二人；第二人接受后编辑，双方可查看结果。验证预算和时间检查、同时编辑时的冲突提示，以及服务重启后的数据恢复。

### V2：信息查询与行程完善

在 V1 上增加：

- Agent 可按需调用高德景点搜索、天气和路线查询工具，展示结果来源及查询时间，并基于查询结果提出方案或调整建议。
- 行程中的交通、住宿、景点可填写开始和结束时间；检查结束早于开始、超出旅行时间范围和时间段重叠。明显无效的时间禁止保存，重叠作为提示供用户确认。
- 记录修改人、时间和修改内容；成员可以留言讨论。费用按交通、住宿、景点等分类展示。

**验收**：成员新增景点后请求 Agent 查询路线并提出调整建议；用户确认保存。检查时间冲突提示、留言与修改记录，以及高德不可用时的明确提示。

### V3：团队决策与总结

在 V2 上增加：

- 成员添加景点或住宿候选项并投票，查看投票结果；用户决定最终选项。
- 记录预算上限与实际支出，展示预计总额、实际总额、差额和按成员人数计算的人均费用。
- Agent 综合已有预算、投票、路线和天气信息，提示潜在风险、说明建议依据；用户确认后才修改正式方案。
- 导出行程、成员、路线和预算的文本摘要，并支持已结束方案归档。

**验收**：成员添加候选地点并投票，Agent 给出有依据的建议；确认方案、记录费用、导出摘要并归档，重启后数据仍可读取。

## 四、核心业务逻辑

### 自然语言生成方案

用户输入需求 → Agent 提取关键字段 → 缺少必要信息时追问 → 生成包含日期、安排与费用的草案 → 系统校验可识别字段 → 用户修改并确认 → 保存。Agent 生成的草案不自动成为正式行程；价格、开放时间等未核实内容需标明。

### 邀请与权限

创建者输入受邀账号 → 系统创建待处理邀请 → 受邀用户登录并接受或拒绝 → 接受后成为方案成员。仅创建者可邀请、移除成员和删除方案；成员可编辑方案或退出。服务端对每次访问和修改检查账号身份及成员权限。

### 预算与时间

总预算为方案中各项预计费用之和；无费用数据的项目标为待填写，不当作确定的零费用。出发、返回时间及各安排时间按统一时区解析；V1 检查整体日期，V2 起进一步检查各安排的时间范围与重叠。

### 文件持久化与并发

服务端负责读取和写入数据，客户端不直接改写共享文件。每次保存先验证权限、输入和版本，再以临时文件写入并替换原文件；失败时保留原数据并报告错误。服务端串行化文件写入，避免同时写入破坏文件。首次启动无数据文件时初始化；读取损坏文件时报告错误，不自动覆盖原文件。

## 五、技术框架

- **客户端**：Java 控制台程序，提供菜单、输入校验和 HTTP 请求。
- **服务端**：Java + Spring Boot，负责账号认证、权限、业务处理、Agent 调用和文本文件读写；多个客户端通过网络访问同一服务。
- **数据存储**：服务端使用 UTF-8 JSON 文本文件保存账号、邀请、方案和版本等结构化数据；不使用数据库。密码只保存经过成熟密码哈希算法处理的结果。
- **Agent 与接口**：DeepSeek 负责理解需求和生成建议；V2 起对接高德 Web 服务作为景点、天气、路线工具。可评估 Spring AI 的工具调用能力，实际选型前核实框架与 DeepSeek 接口兼容性。密钥通过环境变量配置。
- **构建与测试**：Maven 管理项目，JUnit 测试预算、时间、权限、文件恢复及并发冲突；外部服务用测试替身覆盖失败情况，并单独验证真实接口。
- **面向对象**：以旅行方案为基础类，短途周末游与长途跨省游为子类型；交通、住宿、景点和费用为业务对象，通过接口封装文件存储和外部查询。继承与多态应体现真实业务差异，不为展示而强行增加规则。

## 六、约束和风险

- 服务端需要一台成员可通过网络访问的电脑；服务关闭或网络中断时，其他电脑无法共享编辑。
- 本地文本文件适合课程项目规模；它不等于自动备份，也不适合未经设计的大规模并发。应定期备份服务端数据文件。
- V1 未使用实时地点和天气数据；V2 的高德接口权限、额度和费用需在接入前核实。外部调用失败时，本地行程管理仍可使用。
- 背景材料提到 32 课时要求，若实际安排不同，建议与指导教师确认；优先交付完整的 V1，再依次升级。
