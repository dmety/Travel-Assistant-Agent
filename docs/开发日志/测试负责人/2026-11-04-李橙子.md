## 六、问题与处理

- **`git fetch` 失败时不能直接判"无更新"**：本轮首次 fetch 报 `RPC failed; curl 52 Empty reply from server`，随后直连 `github.com:443` 超时（约 75 秒），但 `api.github.com` 可正常访问（200 / 0.45 秒）。此时本地 `origin/main` 仍是旧值，`rev-list HEAD..origin/main` 会返回 0，**这是假阴性**。处理方式：先用 GitHub API 取 `main` 最新 SHA，确认真有差异后重试 `git fetch`，第 2 次即成功。
- **冒烟脚本第一版全线假 FAIL**：zsh 默认不对变量做分词，把 `--noproxy * -s -m 15` 当成单个参数传给 curl，导致 14 项全部失败。改为数组传参后恢复正常。这类"命令参数被整体吞掉"的失败与真实的接口异常表现相似，看输出要留意 curl 自身报错。
- **测试会写脏受跟踪的数据文件**：跑测试与冒烟后 `data/accounts.json`、`data/itineraries.json` 均被修改，提交前已用 `git checkout --` 还原，未进入提交。
- **服务端口**：启动时显式带 `--server.port=8080`，并在启动前清掉环境里的 `SERVER__PORT`，避免 Spring 宽松绑定把端口绑到别处或抢占宿主进程端口。
