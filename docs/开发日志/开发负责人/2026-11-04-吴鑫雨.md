### 1. D-6（P0）乐观锁在并发下失效

**根因**：`ItineraryService.updateXxx` 的「读取 → 校验版本 → `store.save`」三步不是原子操作。
`ItineraryStore.save` 虽然是 `synchronized`，但版本校验发生在进入这把锁**之前**，
多个线程可同时通过校验，后写覆盖前写。

**修复**：给 `ItineraryService` 增加**按行程 id 分片的写锁**（64 个 stripe，固定长度避免锁表无限增长），
把「读取 → 权限校验 → 版本校验 → 校验业务字段 → 写入」整体放进临界区：

```java
private <T> T inWriteLock(String id, Supplier<T> action) {
  synchronized (writeLocks[Math.floorMod(id.hashCode(), LOCK_STRIPES)]) {
    return action.get();
  }
}
```

选型对比：

| 方案 | 结论 |
|---|---|
| 把 CAS 下沉到 `ItineraryStore`（`compareAndSet(id, expected, mutator)`） | 也能解决，但会让 infrastructure 层反向依赖 application 层的 `VersionConflictException`，分层倒置 |
| 对 Service 写方法整体 `synchronized` | 最简单，但所有行程的写操作串行，跨行程也互相阻塞 |
| **按 id 分片加锁（采用）** | 同一行程严格串行（正确性所需），不同行程几乎无竞争；不破坏原有分层 |

锁顺序固定为「Service stripe 锁 → Store 锁」，不存在反向获取路径，无死锁风险。

### 2. D-4（P0）费用金额允许为负数

`updateExpenses` 增加 `validateNonNegativeAmounts`：`amount.signum() < 0` → 400。
`amount` 为 `null` 视为未填，不拦截（避免把「暂未填金额」判成错误）。

### 3. D-5（P1）住宿离店早于入住

`updateLodgings` 增加 `validateLodgingPeriods`：`checkOut.isBefore(checkIn)` → 400。
任一日期为空则不校验（与「字段可暂缺」的现状保持一致）。

### 4. D-1（P1）可邀请未注册账号

`addMember` 注入 `AccountStore`，写入前校验 `accounts.exists(name)`，不存在 → 400。
同时补 `username` 空白校验（此前空字符串也能写进成员列表）。

### 5. D-2（P2）创建行程不校验标题

两层：
- 接口层：`CreateItineraryRequest.title` 加 `@NotBlank`，控制器加 `@Valid`；
- 领域层：`ItineraryService.create` 再判一次 `null`/`isBlank`（防止绕过 Web 层直接调用服务）。

标题入库前 `trim()`，避免 `"  杭州  "` 这类值污染列表。

### 6. D-3（P2）修改不存在的成员静默成功并递增版本号

`updateMember` / `removeMember` 改为先定位成员下标，`index < 0` → 抛 `MemberNotFoundException` → 404，
不再产生「无变化的写」和「无意义的版本递增」。

> 顺带说明：测试日志只点了 `PUT`，但 `DELETE` 是同一根因（都不校验成员存在性），一并修了。

### 7. 测试用例转正

删掉 `KnownDefectTest`（6 条）与 `OptimisticLockConcurrencyTest`（1 条）上的 `@Disabled`，
断言保持「需求要求的正确行为」不变，现在作为**常驻回归门禁**：谁把校验改回去，构建立刻变红。
