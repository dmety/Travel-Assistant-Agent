| 场景 | 结果 |
| --- | --- |
| 八达岭 11 月成人 | 35 元（淡季价） |
| 八达岭 11 月学生 | 17.5 元（学生淡季价） |

## 三、缺陷清单

### T-1（P2）未填游客时「门票估算」显示 0 元

**现象**：填了日期、景点，但游客列表为空时，接口返回 `estimatedTotal = 0`，前端据此渲染「门票估算：0 元」；同一响应里又追问「请添加每位游客」，两处自相矛盾。

**复现**：

```
POST /api/agent/tickets/advice
{"message":"","needs":{"attraction":"八达岭长城","date":"2026-11-10","product":"STANDARD","visitors":[]}}
→ estimatedTotal: 0，questions: ["请添加每位游客（无需姓名、证件号）"]
```

**根因**：`TicketAssistantService` 计算合计时只判断了 `visitors != null`，空列表也能进入，`total` 初始化为 0 后循环不执行，于是以 0 收场。

```java
if (inRange && visitors != null && date != null) {
  total = BigDecimal.ZERO;
```

**建议修法**：加一个非空判断，游客为空时不计算合计。

```java
if (inRange && visitors != null && !visitors.isEmpty() && date != null) {
```

**判定依据**：项目自身在票务上反复强调「未知费用不能当作免费」「票价缺失保持未知不补 0」，此处 0 元属于同一类错误，只是发生在合计而非单价。当前有追问兜住，不会真被当成免票下单，故判 P2 而非 P1。

## 四、功能缺口

1. **票务规则只覆盖北京 3 个景点**（八达岭长城、首都博物馆、中山公园）。其他城市与景点只能走「查官方入口」，没有票价分档。这是当前交付范围，不是缺陷，但需要在使用说明里写清。
2. **不含下单、支付、出票**。购票登记是用户自报，系统不校验真实性，也不产生费用。这一条与需求文档的实现边界一致。
3. **模型解析分支未实测**。本机没有 `DEEPSEEK_API_KEY`，全程走「结构化表单 + 规则判断」，响应里也明确标注「本轮使用结构化表单和规则判断（无模型调用）」。自然语言提取景点、日期、人数的分支至今没有跑过一次。
4. **余票与实时价格不核验**，提示里已写明「费用仅为人工核验快照估算，不是实时售价」。

| 断言 | 我的预期 | 实际 | 结论 |

| 匿名带 `activityId` | 403 | 200 | 我把 `activityId` 放进了 `needs` 里，服务端读的是顶层字段，等于没传 |

修正参数层级后，`{"activityId":"x"}`（无行程）正确返回 400「活动必须关联行程」。

**教训**：FAIL 出现时先核对请求体结构，再判定是不是缺陷。这次两分钟就排除了，如果直接写进缺陷清单，开发会白查一轮。

### 6.2 一次命令被安全策略误拦

探测脚本里把辅助函数命名为 `reg`（record 的缩写），触发系统工具拦截规则，整条命令被拒。改名 `put_ticket` 后正常。

**教训**：脚本里的函数名、变量名避开 `reg`、`sc`、`wmic`、`schtasks` 这类系统工具名，否则会被安全策略当成系统命令调用。
